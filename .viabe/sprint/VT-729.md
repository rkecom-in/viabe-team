# VT-729 — the "dev degradation" was not degradation

## What I reported, and why it was wrong
During the VT-720 ×3 I saw 90s TIMEOUTs, `terminal=running`, and `route='none'` on turns that had
been stable across three prior baselines, and told Clau dev looked degraded. It wasn't. **I was
restarting the service under my own measurements.**

## Root cause
**Railway's native auto-deploy fires on EVERY push to `dev` — including docs-only pushes that the
VT-245 CI trigger-diet deliberately skips.** A skipped CI run does not skip the deploy. So a
`docs(sprint): …` push, which looks completely inert, restarts the orchestrator.

Evidence, from the deployment list against `git log`:

| deployment | UTC | pushed commit |
|---|---|---|
| `007603c4` | 14:41:46 | `a70076ae` — **docs-only** (VT-726/727 roster) |
| `886b6ff8` | 13:58:16 | `25a29dca` |
| `662f21a2` | 13:27:23 | `9ac07465` |

The service logged `DBOS launched!` at **14:42:58** — squarely inside the v4 run, whose run 1 was
clean, run 2 failed with the route unobserved on a still-`running` turn, and run 3 timed out at 90s.
That is one measurement split across two services.

## Proof
Re-ran the same scenario with the service stable and no push in flight:

```
run 1/3: clean (route=none, terminal=completed)
run 2/3: clean (route=none, terminal=completed)
run 3/3: clean (route=none, terminal=completed)
=== summary: 1 critical scenario(s), 0 block(s) ===
```

`routing_db_proof_finance_vs_sr` — **3/3 clean**. Nothing was wrong with dev. With this, **all four
VT-720 casebook classes are dead 3/3.**

## The fix — make it self-announcing, not a discipline note
`run_critical_x3.py` now reads `dbos.application_versions` (DBOS writes one row per deployed
version) **before and after each scenario** and compares. A change means the observations describe
two different services, so the run is reported as **CONTAMINATED**, never as a BLOCK:

```
!! CONTAMINATED: the orchestrator REDEPLOYED during this scenario (abc… -> def…).
   TIMEOUT / terminal=running / unobserved-route results below are measurement artifacts,
   NOT product behavior. Re-run on a stable service before drawing any conclusion.
```

Cross-run divergence on a contaminated scenario is likewise reported as contaminated, since a
redeploy makes divergence expected rather than informative. Exit stays non-zero — the run still
needs redoing — but the label no longer lies about *why*.

A discipline note ("hold pushes during runs") would not have saved me: I *was* holding code pushes.
It was the docs push I did not think of as a deploy. The guard does not depend on remembering that.

## Why this mattered more than it looks
A contaminated run recorded as a product failure sends the next session hunting a bug that was never
there — and I had already started down that path, bounding a compose timeout to chase a latency
problem that was partly self-inflicted. The reverse is worse: a contaminated run that happens to
pass reads as proof.

## Follow-on, not done here
`--keep-tenants` aside, teardown deletes the tenant and cascades its `pipeline_runs` away, so
after-the-fact latency forensics on a finished run are impossible (only 1 run row survived 8 hours
of measurement). Not fixed here; noted because it is why the diagnosis had to be reconstructed from
deploy timestamps rather than from run timings.
