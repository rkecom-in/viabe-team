# VT-772 — the instrument destroys the evidence, then the absence is read as a defect

## What happened, concretely

VT-725 gate (a) needed one thing: a real deployed turn writing `decision_evidence_links` rows keyed
`manager_turn:…`. Every run showed **zero** such rows — across two builds, a key fix, and a redeploy.
I concluded the serving seam was never reached on the live path, wrote that into the row, the
objectives file and two signals, and moved a call site on the strength of it.

**The zeros were the harness.** `run_full_pack` / `convo_harness` delete the throwaway tenant at
teardown — the run's own output prints `[teardown] tenant … deleted; tenant rows left = 0` — and
`decision_evidence_links.tenant_id` cascades. The rows were written during the turn and destroyed
before any query could see them. The identical scenario re-run with `--keep-tenants` produced **200
rows** from the same code path.

## Why this is worth a row rather than a note

The failure mode is not "a test was flaky". It is that **the instrument produces the exact signature
of the defect it is supposed to detect**, silently, for any feature whose output is a persisted row.
Shadow features are precisely that kind of feature: they change no reply, so a row is the ONLY
evidence they ran. So the harness is at its least trustworthy exactly where we most need it, and the
absence is indistinguishable from a real miss without knowing about the teardown.

It also survived review three times: the canary passed, the wiring test passed, and the deployment
reported SUCCESS — none of them touch this.

## The fix

1. **`--keep-tenants` becomes MANDATORY, not optional, for any scenario whose acceptance is a
   persisted row.** The scenario declares that it asserts on persistence; the runner refuses to grade
   such a scenario without tenant retention rather than reporting a clean zero.
2. **Teardown must not silently invalidate an assertion made against it.** Where retention is off and
   a persistence assertion exists, the result is **INDETERMINATE**, never PASS and never FAIL — the
   same label VT-753 established for unmeasured, and for the same reason: an unmeasured gate must
   never be counted as a failed one, nor as a passed one.
3. **A reaper for retained tenants**, so mandatory retention does not leak dev tenants. Retention is
   for the duration of the assertion, not forever.

## Exit gate
(a) A scenario declaring a persistence assertion cannot be graded without tenant retention — proven
by a deliberately-broken variant that fails RED once. (b) Retained tenants are reaped on a bounded
schedule and the reaper is proven to leave an in-flight assertion alone. (c) The VT-725 gate (a) proof
is reproducible from a clean run without hand-passing a flag.

## The wider lesson, recorded because it generalises past this harness
**Absence of evidence produced BY the measuring instrument is not evidence of absence.** Before
reading a zero as a defect, establish that the instrument would have let a non-zero survive. That
check costs one run with retention on; skipping it cost a wrong diagnosis that reached three
documents and a code change.
