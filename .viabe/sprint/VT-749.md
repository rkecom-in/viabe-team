# VT-749 — unscoped cards match everything, and the hedge that was supposed to stop it is decorative

## The measurement (reproducible, no DB needed)

Built the v3 shadow plan from the committed corpus artifacts
(`build_full_plan` → `build_resolution_plan` over `source_rights.jsonl` + `candidate_cards.jsonl`
+ `deferral_resolution_delta.jsonl`):

| | |
|---|---|
| v3 members | 118 |
| `retrieval_eligible` | **100** |
| **eligible AND scoping nothing** (no jurisdiction, size band, industry, maturity stage or channel, and `universal=false`) | **63** |
| eligible with `universal=true` | **0** |
| eligible with no `channels` | 93 |
| eligible with no `effective_from` | 74 |

## Why "unscoped" is not "cautious"

`card_retrieval._dimension_match` (`card_retrieval.py:555-556`) returns `True` for an empty
dimension **without ever consulting the context value**, and appends an `unknown_<dim>` hedge.
`_applicability` (`:560-585`) hard-filters only on the effective window. So all-empty +
no window = **applicable to every possible context**, with six hedge reasons attached.

What the hedge costs: `applicability_score = max(0.0, 1.0 - 0.15 * len(unknown_dimensions))`
(`:285`), weighted `0.08` of seven weights and renormalized — **maximum final-score delta between
an all-empty card and a fully scoped one is 0.083**, against `MEASURED_RETRIEVAL_FLOOR = 0.250`.
And `hedge_reasons` has three consumers repo-wide (`:336`, `:498`, `canaries/o11_knowledge.py:150`)
— **stored, copied, printed. No profile, gate, filter or threshold reads it.** It is a label.

The function's own docstring says empty is *"treated as UNKNOWN on that dimension, not as
unrestricted"* (VT-736 note, `:540-556`). The code does the opposite. `card_serving.py:88-91`
closes the mirror-image hole on the CONTEXT side by hardcoding `_JURISDICTION = "IN"`, with a
comment naming exactly this risk — the CARD side was left open.

## Why this is not fixable as a contract validator (tried, reverted)

Adding `retrieval_eligible ⇒ scoped or universal` to `KnowledgeCard._governance_invariants`:
- **breaks the existing v3 plan build** — 22 tests + 10 errors, because the plan itself promotes
  those 63 cards;
- worse, it would **break rehydration of already-persisted rows**: `registry_seed._card_from_row`
  → `model_validate`, and `card_serving.py:546` **raises rather than degrades**. Dev already holds
  these rows. A validator would take the serving path down the first time it read one.

So enforcement cannot precede the data. That is the whole shape of this row.

## Scope

1. **Decide the scoping for the 63** — this is product judgment, not a heuristic. Every card either
   gets at least one honest dimension or declares `universal=true` and means it. Root cause is
   builder-side: `convert_o8_candidates.py:_jurisdiction` (`:238-260`) is a casefold **substring
   match** against a seven-token list (`"india"`, `"gst"`, `"msme"`, `"rbi.org.in"`, …) — it missed
   21 of VT-723's 33 and 63 of the 100. **This is exactly the class Fazal's standing no-lists rule
   names**: a keyword list standing in for a judgment.
2. **Then** add the eligibility-boundary invariant (the reverted validator, re-applied once the
   data can pass it), plus the test that an unscoped card cannot become retrieval-eligible.
3. Decide whether the `unknown_*` hedge should carry weight at all, or be replaced by an explicit
   ineligibility — a 0.083 penalty that nothing reads is worse than no penalty, because it reads
   as a control in review.

## Sequencing

**Not a VT-723 blocker** — VT-723's 33 cards are all `retrieval_eligible: false` and land in
shadow, so nothing they declare is consulted by anything.

**It IS a VT-725 blocker.** S2 wires the retrieval call site. The moment retrieval serves the v3
corpus, 63 cards are eligible for every tenant, every channel, every jurisdiction, and the
`o11` recall figure of 0.229 was measured under exactly that condition — which means the recall
number itself is partly an artifact of cards that match indiscriminately.

## Gates

(a) the count above reproduced from the committed artifacts, as a test, so it cannot drift silently ·
(b) every one of the 63 carries an explicit scope or an explicit `universal` with a reason ·
(c) the eligibility invariant lands and the plan still builds ·
(d) rehydration of persisted rows proven unbroken against a real DB (the failure mode a validator
would have caused) · (e) recall re-measured after scoping, so we know whether 0.229 was inflated
or depressed by indiscriminate matching.

### THE TRAP — the delta's ids are not the rows serving reads

This is the finding worth carrying forward. The delta names each card by `card_version_id`, and all 63
of those ids exist in `knowledge_cards`. **None of them is a member of the served corpus:**

```
delta targets that ARE v3 (served) members : 0        (only 7 are members of v2)
v3 members that are eligible AND unscoped  : 63       <- the rows that actually matter
delta card_keys ∩ v3 member card_keys      : 63       <- same LOGICAL cards, different version rows
```

Keying the landing on those version ids would have minted 63 new versions of rows nobody serves,
reported "63 cards scoped", passed every count I had written, and **left the served corpus matching
every tenant exactly as before.** The migration therefore resolves each target as *the served member
sharing that card_key*, and asserts the join is 63 rows and 1:1 before writing anything. Keying on
`card_key` is also the more honest key: a scoping judgment is about the logical card, not about one
serialization of it.

`registry_scoping` joins on `card_id` for the same reason — the plan's key — and records
`card_version_id` for the database step rather than pretending one key addresses both layers.

### Clau's review bar, exercised rather than rubber-stamped

Two calls looked wrong to me from the claim lines and I read the full bodies before landing:

- **`decision_process` → ST** looked like a pure judgment card that micro tenants should see. Its note
  names *proposer, independent challenger, Decider and implementation owner* as four distinct people
  with a senior sponsor — a 1–2 person kirana has none of that. **Clau's call stands.**
- **`pricing` → OP** looked like ordinary price-setting, which every shop does. Its claim key is
  `adaptive_pricing_requires_an_approved_learning_budget…` — randomized exploration over reusable
  product attributes, which needs an online surface. **Clau's call stands.**

I accepted all 63 with no overrides, having checked the two most likely to be wrong.

### Two defects in my own migration, both caught before they could mislead

1. **It opened its own `BEGIN`/`COMMIT`.** `apply_migrations` already wraps each file in
   `conn.transaction()`, so my `COMMIT` ended the RUNNER's transaction — a dry-run probe that raised in
   order to roll back had nothing left to undo and **the write landed for real**. Removed; a migration
   must never take transaction control away from the runner. (The landing that escaped was verified
   correct and is the state now recorded, but it escaped by accident, which is the point.)
2. **It was not idempotent**, so the retry failed on a duplicate primary key rather than being a
   no-op. Now guarded throughout, which is what a migration should have been to begin with.

Also fixed along the way: `c.version + 1` collided with an existing version-2 row on one `card_key`
(the next version for a LOGICAL card is `max(version)` over its key, not the member's own version + 1);
`knowledge_cards.corpus_version_id` is an FK, so the corpus-version row has to be inserted first; and
`knowledge_card_embeddings.embedding_dimensions` is NOT NULL and had to be carried across.

### Still open

**Scope 2 — the contract invariant** (`retrieval_eligible ⇒ scoped or universal`). It was tried and
reverted before because *enforcement cannot precede the data*; the data now supports it, so it is
buildable. It needs care with REHYDRATION: `registry_seed._card_from_row` → `model_validate` and
`card_serving` RAISES rather than degrades, so the validator must not be able to take the serving path
down on a pre-v4 row that is still legitimately in the table.
