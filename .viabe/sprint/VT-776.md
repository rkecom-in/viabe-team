# VT-776 — name→GSTIN discovery: new fetcher, real secondary, cascade

## Why

Three separate problems converged on the same leg.

1. **Cost.** ScrapingBee's floor is $20 / 75k credits. Wrong order of magnitude for launch.
   Firecrawl's entry plan is ~1000 requests/month, which fits actual signup volume.
2. **Reliability.** knowyourgst.com is not dependably up. A single-source discovery leg means
   "we couldn't find your GSTIN" whenever that one site is down.
3. **Two latent defects** found while diagnosing Fazal's failed dev onboarding (see below).

## What shipped

**1. Fetcher swap (5be0fe45).** `_scrapingbee_fetch` → `_firecrawl_fetch` against
`api.firecrawl.dev/v2/scrape`. Same form, same selectors, same 6s render wait. `_parse_results`
untouched — a fetcher swap, not an extraction change. The key moves from a query PARAMETER to the
Authorization header, which removes the shape that leaked it.

**2. Dedicated `discovery` model tier.** Was bound to `complex`, which also serves the Manager's
reasoning path — one couldn't move without the other. Now `TEAM_MODEL_DISCOVERY` → `gemini-3.5-flash`.
Gemini because this leg is search-grounded EXTRACTION, not reasoning: `google_search` grounding is
native, flash is cheap enough per signup, and the leg already demands strict JSON.

**3. The legs became a CASCADE.** Previously knowyourgst AND the LLM ran on every signup, so a
successful scrape still paid for an LLM call. Now the billed LLM call fires ONLY when the scrape
produced no GSTIN. An injected `llm_fn` opts the leg in without the flag but does NOT bypass the
cascade — tested behaviour is production behaviour.

Fallback order is now exactly what Fazal specified:
`Firecrawl/knowyourgst → (only if empty) Gemini+web-search → (only if empty) owner types the GSTIN.`
All three feed the SAME Sandbox verify gate. Discovery only ever produces hints.

## Two defects fixed en route

**(a) ScrapingBee key leak (9efca143).** `_scrapingbee_fetch` called `resp.raise_for_status()`.
httpx puts the full request URL in the exception message and the api_key was a query PARAMETER, so
a 401 raised an exception carrying the live key — and `search` logs it with `exc_info=True`. The key
was written to the logs. **Fazal owes a rotation** (the key is compromised independent of the swap).
Same commit removed `integration.knowyourgst_discovery`, a registry capability with no handler and
no call site whose summary described the leg BACKWARDS ("facts from a GSTIN" when it is name→GSTIN),
sitting beside `integration.gst_verify` in the LLM-facing label map.

**(b) The parser had gone blind (24c130f6).** `_RESULT_RE` required a RELATIVE href
(`/gst-number-search/…`); knowyourgst.com now emits ABSOLUTE URLs. Every row stopped matching while
the scrape still returned HTTP 200 with a full results page — the leg reported 0 candidates, which
is indistinguishable from "this business has no GST registration". **A parser bug was being shown to
the owner as a fact about their company.** Caught only by asserting on ROW COUNT against a
known-resolvable name (Reliance's page carried 43 result units; the parser matched 0).
**This was vendor-independent and would have survived a key rotation.**

## Parity caveat (honest)

The ScrapingBee-vs-Firecrawl diff Clau asked for could NOT be run: ScrapingBee 401s on every call,
so it is **UNMEASURED, not "worse"**. My first harness scored 0-vs-0 as "PARITY", which was a false
green; the verdict logic now labels auth/transport failures as unmeasured rather than folding them
into a comparison.

Firecrawl's structured `json` format also extracts the rows correctly (11s), but it was NOT adopted:
LLM extraction costs more credits and can fabricate a GSTIN. The deterministic regex is free and now
correct. Firecrawl is used for the FETCH only.

No action needed on `TEAM_MODEL_DISCOVERY` (unset both envs → the `gemini-3.5-flash` default applies),
`TEAM_ENABLE_WEB_SEARCH` (set both), or `ENABLE_LLM_DISCOVERY` (set both).
