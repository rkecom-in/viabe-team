# VT-735 — Flex where latency doesn't matter, never where it does

## The design constraint that shapes everything (Clau, binding)
Flex = ~50% cost for DELAYED responses (and occasional resource-unavailable errors that need
retry). **Latency is precisely what we are fighting on owner-facing turns** (the 96s waits, the
D1 ack, the SR timeout class). A blanket flex=true would save rupees by making every owner stare
at WhatsApp longer — the wrong trade, per Fazal's own no-surprises/experience rulings.

So: **flex is a per-call LATENCY CLASS, not a global switch.**

## Scope
1. **Classify every gpt call site** (they all route through the tier seam post-VT-732 — the sweep
   is the inventory): `interactive` (owner is waiting: brain turns, onboarding turn/intent,
   approval resolution, anything in a webhook turn) vs `background` (nobody waits: daily plan
   revision pass, memory distillation, KG population/backfill, impact judgments §7C, monthly
   report generation, eval bundle generation, self-evaluate, entity enrich re-runs).
2. **Env control on Railway (names, per the one-canonical-name rule):**
   `TEAM_GPT_FLEX = off | background | all` — default **background**. `all` exists so Fazal can
   force-test; it is NOT the intended prod posture. Read fresh per call like the tier vars;
   boot-conformance line (VT-731) prints the resolved value.
3. **Provider seam implementation:** pass the service-tier param on openai-family calls only,
   when the call's latency class qualifies. **Verify the exact SDK surface against current OpenAI
   docs (Context7/web) — do not guess the parameter name or the retry semantics.** Handle the
   flex-specific resource-unavailable/timeout: bounded retry, then fall through to standard tier
   (a background job silently paying full price beats a background job failing).
4. **Ledger + pricing correctness (the half everyone forgets):**
   - `llm_call_events.service_tier` already exists — record `flex` on flex calls.
   - `model_pricing` must price (model, service_tier) pairs — flex rows at the flex rates.
     Otherwise VT-733's unit economics silently overstate background costs 2× and the repricing
     brief inherits the error.
   - **DISCREPANCY RESOLVED (Clau, 2026-08-06, verified against
     https://developers.openai.com/api/docs/pricing): FAZAL WAS RIGHT — the registry is 5×
     STALE.** OpenAI cut prices. Verified figures, USD per 1M tokens, SHORT context
     (long-context = 2× these, threshold per docs):
     | tier | input | cached-in | cache-write | output |
     |---|---|---|---|---|
     | gpt-5.6-luna standard | 0.20 | 0.02 | 0.25 | 1.20 |
     | gpt-5.6-luna **flex** | 0.10 | 0.01 | 0.125 | 0.60 |
     | gpt-5.6-luna batch | 0.10 | 0.01 | 0.125 | 0.60 |
     | gpt-5.6-luna fast | 0.40 | 0.04 | 0.50 | 2.40 |
     Also: terra standard 2.00/12.00 (flex 1.00/6.00) · sol 5.00/30.00 (flex 2.50/15.00).
     **Refresh EVERY OpenAI-family row in the registry from this sheet** — if luna is 5× stale,
     assume the rest are too. Cite the source URL + fetch date in the config/migration comment.
     `service_tier` is confirmed as the API parameter family (docs: `"flex"`, and
     `"priority"`→`"fast"` renamed 2026-07-30).
   - **Two free findings from the sheet, note in the row close (no build now):**
     (a) **Batch API prices equal Flex** — for fully-offline work (eval bundle generation,
     nightly rollups) the Batch API is an equivalent-discount alternative with no
     resource-unavailable retry class; consider at VT-733-C time.
     (b) **Fast mode exists at 2× price** — a future latency lever for the approval-resolution
     path if the D1/arm latency work (VT-730) wants it; Fazal's call, costs double, park it.
5. **Prove it:** one background call (e.g. a distillation run) on dev shows `service_tier=flex`
   in the ledger with the flex price attributed; one interactive turn shows standard tier
   untouched; flip `TEAM_GPT_FLEX=off` → zero flex calls (env sovereignty, VT-732 standard).

## Boundaries
- **Never flex on judge/eval scoring calls** used for gates — a gate that flakes on
  resource-unavailable is a gate nobody trusts. (Bundle GENERATION may flex; judge scoring not.)
- No prod env changes (Fazal's, CL-431). Dev default = `background` once proven.
- Does not enter the NOW chain; lane work, deploys ride batch windows, no pushes during packs.
- Brain-touching only at the seam parameter level — if the ×3-gate question arises, the answer
  is: interactive paths are UNTOUCHED by construction; prove that claim in the diff, then the
  full gate is not owed. If flex leaks into an interactive path, that construction failed —
  redesign, don't re-gate.

**Consequence, stated because it changes a number Fazal has already seen:** dev runs entirely on

the VT-733 cost console has reported was **5× too high**.

`pricing.py`'s seed mirror moved in lock-step with the migration — the PG drift guard asserts the
two are equal, which is what forced them to land as one change. Flex/batch remain 0.5× via the
existing `discount_multiplier` and reproduce the sheet exactly (luna flex 0.10/0.60); cached-in
stays 0.1× (luna 0.02 against 0.20). Verified: 31 migration + 54 llm tests green on a fresh cluster.

**Two design calls, recorded:**
1. The Fast 2× premium does NOT ride `discount_multiplier` — that field is a per-MODEL batch
   DISCOUNT, so sharing it would bill a Fast call at HALF price on any flex-discounted model,
   under-reporting exactly the tier the policy spends most per token on. It is
   `_PREMIUM_TIER_MULTIPLIERS` in `llm/pricing.py`.
2. No `fast_multiplier` DB column yet — the 2× is a uniform published rate, not per-model, so the
   column would be schema nothing reads. It earns its place when a model prices its fast lane
   differently.
