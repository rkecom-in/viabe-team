# VT-730 — never ask a question you cannot yet hear the answer to

## Fazal's question, which is the design
*"Why aren't we awaiting for the Manager to be ready to listen, before asking the question?"*

There is no good answer. The current code asks first, then gives the reply a 96-second bounded
head-start (`_APPROVAL_ARM_WAIT`) hoping the arm lands in time. That is a race with a timeout as
the referee — and every timeout on a race is a guess. Fazal's second point is equally right: 96s is
"the observed chain plus headroom," and the first slow specialist call, retry, or cold start makes
the guess wrong, silently, on a money path.

The wait treats the symptom. This row removes the disease. Three parts.

## Part 1 — THE INVARIANT: arm-before-ask, enforced at the choke

**No decision-shaped message reaches the owner unless the decision is already resolvable.**

- An approval-ask may be EMITTED only when its `pending_approvals` row is already
  `status='armed'`. The correct order already exists in ONE path —
  `request_owner_approval.py`: *"pending_approvals row INSERTed THEN template sent."* This row
  makes that the only legal order everywhere.
- **Enforcement is structural, not disciplinary:** VT-718 gave us the single emission choke every
  owner-bound send passes through. The choke gains a check — a message classified as an
  approval-ask (it already carries the approval id for the ledger; VT-719 records it as a
  commitment) is REFUSED emission if its approval id does not reference an armed row. Refusal is
  loud: it is a defect signal, never a silent drop.
- Consequence: the ask/arm race cannot be *written* anymore. The same construction standard as
  VT-725's no-text-field shadow types and VT-726's pipeline-enforcing seed plan: make the wrong
  thing inexpressible, don't police it.

## Part 2 — THE MAILBOX: replace both 96s polls with durable, event-driven resolution

The two `DBOS.sleep` poll loops in `runner.py` (`_D1_INTURN_WAIT`, `_APPROVAL_ARM_WAIT`)
re-implement — inside a SYNCHRONOUS webhook turn — what DBOS provides natively and durably
(validated against current DBOS docs via Context7, 2026-08-05):

- `DBOS.send(workflow_id, message, topic)` / `DBOS.recv(topic, timeout)` — exactly-once durable
  messaging between workflows, Postgres-backed, survives crash/replay.
- `DBOS.set_event` / `DBOS.get_event(workflow_id, key, timeout)` — durable state a waiter blocks
  on. Their own canonical example is a billing workflow durably awaiting a payment decision.

**Target shape:**
- The webhook turn NEVER spin-waits. An owner reply that is a clear decision with no armed
  approval yet (legacy/edge only, once Part 1 holds) is persisted as a **parked decision row**
  (tenant, sid, verbatim body, classification, ts) and the turn completes instantly with an
  honest ack. Nothing is held in memory; nothing depends on the process surviving.
- The arming code's LAST step — transactionally with the arm — checks the mailbox: a parked
  decision for this approval resolves it immediately (opt-out/DSR guard re-runs first, as today).
- The delegation/manager_task workflow signals its owner-bound reply via `set_event`/`send`
  rather than being polled for. The turn subscribes (`recv`/`get_event`) with a SHORT courtesy
  window (single-digit seconds) purely for the one-beat UX; past it, honest ack now, real reply
  when ready. **A timeout may only ever cost elegance, never correctness.**
- Both 96s constants and their comment-essays are DELETED, not retuned. If a bounded wait
  survives anywhere, its expiry must be a logged fallback to a correct path, never a dropped
  decision.

## Part 3 — LIVENESS: no process death may strand a job silently

Fazal: *"how we know that if one process has died that has not left the job stranded."* Standing
contract, this row + VT-634:

1. **Every owed reply has a durable deadline.** Any workflow that owes the owner a message
   records (workflow_id, tenant, owed_kind, deadline) at spawn — in the DB, not in memory. A
   watchdog (DBOS scheduled workflow) sweeps past-deadline debts: emit the honest fallback, mark
   the workflow suspect, surface on the VTR console. An owner may wait; they may never wait
   *forever, silently*.
2. **Every armed approval has a TTL + disposition.** Expiry is an explicit lifecycle event
   (owner told, VTR informed) — never a row that quietly rots. The 2026-05-21 orphan class.
3. **Parked decisions have a TTL** with the same explicitness: "I got your yes but could not
   act on it" is an incident surfaced to VTR, not a stale row.
4. **Recovery is assumed hostile:** per CC's `compute_app_version` finding, restarts re-recover
   PENDING workflows with the same version hash. Every waiter/watchdog step must be
   replay-deterministic (the existing checkpointed-poll discipline carries over to recv/events).

## Sequencing and boundaries
- **After the current re-drive completes and the promotion ships.** This is brain-and-money-path
  surgery; it does not jump the queue ahead of a promotion that is otherwise ready — rushing it
  into that window is how ordering bugs get made. Fazal may overrule.
- Full-pack ×3 mandatory (brain-touching). The nine SR gate scenarios are the acceptance set —
  they must pass at a NORMAL harness timeout once the polls are gone, because nothing should wait
  ~96s anymore.
- The 96s product budget is not "retuned" as part of this row; it is made obsolete. If any
  residual wait needs a number, that number is a UX courtesy window and Fazal approves it.
- Effect gates unchanged: none of this touches WHETHER a send is allowed — only how the question
  and answer are carried. Pillar-7 and the deterministic gates remain the sole effect authority.
