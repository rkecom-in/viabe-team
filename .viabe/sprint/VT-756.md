# VT-756 — an absence of data reported as a measurement

## What the owner was told

Deployed dev, tenant `639965a2`, scenario `m_conversation_hinglish_status_smalltalk`, step 1:

```
owner:     (code-mixed status ask)
assistant: You currently have 0 customers in your ledger.
```

The tenant is `--onboarded` with **no data source connected and no seeded rows**. So "0" is not a
measurement — there is nothing to measure. The scenario's own note states the requirement exactly:

> *"Code-mixed status ask with **no data connected**. Expect an honest 'not connected yet' class answer —
> **never a fabricated zero-count as if it were real data**."*

**"You have 0 customers" and "you haven't connected your customer data yet" are different claims.** The
first says we looked and found none; the truth is we have nothing to look at. An owner reading the first
one reasonably concludes their business has no customers on record — or that Viabe lost them.

## The mechanism, and why it is embarrassing rather than hard

`owner_inputs/status_query.py:612-614`:

```python
if qtype == "customer_count":
    n = CustomersWrapper().count_all(tenant_id)
    return f"You currently have {n} customers in your ledger."
```

No connection check. It counts rows and states the number.

**The honest pattern already exists FOUR LINES BELOW**, in the sibling branch of the same function:

```python
if qtype == "top_spend":
    ...
    if not ranked:
        return (          # <- degrades to an honest "not available yet" answer
```

So `top_spend` handles empty honestly and `customer_count` does not, in the same function, written by the
same hand. This is not a missing capability; it is one branch that never got the treatment its neighbour
got.

## Why the fix is not simply "if n == 0, say not-connected"

Zero has **two** causes and they warrant different sentences:

| cause | honest answer |
|---|---|
| no source connected / no data ingested | *"I don't have your customer data yet — connect a source and I'll pull it in."* |
| a source IS connected and genuinely returned zero rows | *"Your ledger is connected and currently shows no customers."* |

Conflating them replaces one wrong answer with another. **The connected/not-connected fact already exists
in the codebase** — `journey._connected_integrations` (`journey.py:2604`) reads whether data has actually
LANDED (phase_5_confirmed, not merely OAuth-connected, which is the right definition). It is
journey-private and `status_query` never learned it. So this is the *built-and-not-consulted* shape again,
not a greenfield need.

## Scope

1. **Promote the connected-truth read** out of `journey`'s privates into something `status_query` can
   call, keeping its definition intact (data LANDED, not a token existing) and its fail-soft posture.
2. **`customer_count` answers from BOTH facts**, count and connection, with the two distinct sentences
   above. Fail-closed toward "not connected yet" on an unknown connection state — an over-cautious
   "connect a source" is recoverable; a false zero is a trust loss.
3. **Audit the other `classify_status_query` branches for the same shape.** `top_spend` is already honest;
   check every remaining qtype for a bare aggregate reported without its connection precondition. The
   defect is a class, not a line.
4. Keep the deterministic fast-path deterministic — this needs **no LLM**. It is two reads and a branch,
   and the Pillar-1 gate on this path forbids a model call anyway.

## Boundaries

- **Do not answer with a number the owner cannot act on.** The rule this row asserts: a count is only
  honest when its data source is known to be present.
- Do not route this to the brain to "phrase it nicely". The fast-path exists because the classifier
  mis-routes status asks; sending it to the model reintroduces VT-600's deflection problem.
- No PII: counts and connection state only (CL-390), exactly as today.

## Exit gate

(a) A tenant with NO connected source asking for a count gets the not-connected answer and **never a
numeral** — proven on deployed dev, not asserted. (b) A tenant WITH a connected source and genuinely zero
rows gets the connected-and-empty answer, so the fix did not just swap one lie for another. (c) A tenant
with real rows still gets its count unchanged. (d) `m_conversation_hinglish_status_smalltalk` passes.
(e) Every other `classify_status_query` branch is enumerated with its connection precondition stated or
shown unnecessary.

## What was built (2026-08-15)

`orchestrator/integrations/connection_truth.py` — `customer_data_source_connected(tenant_id)`.

The fact existed THREE times already, each private to its caller and each with a different
definition, which is why no caller could answer the honesty question:

| reader | definition | scope |
|---|---|---|
| `journey._connected_integrations` | `phase_5_confirmed` — data has LANDED | journey-private, single `current_connector_id` |
| `integrations.commit.is_connector_connected` | a `tenant_oauth_tokens` row | per connector |
| `connector_first_contact._connected_or_healthy` | oauth row OR enabled+ok status row | per connector |

All three ask *"is connector X connected?"*. The honest answer needs *"is ANY customer-data source
connected at all?"* — the union, connector unpinned. The two-source half matters: a status-only
tenant answered "not connected" against a healthy syncing connector (the reconnect_broken_sync
fabrication residual, §2 judge 2026-07-11), so an oauth-row-only read would have re-created that bug
inside the fix for this one.

**Fail-CLOSED**, inverting the usual posture on purpose (scope 2): any read failure → "not
connected". An over-cautious "connect a source" toward an owner who has one is recoverable; a
fabricated zero is a trust loss.

**`customer_count`** now branches on both facts. `n > 0` short-circuits with the original sentence
byte-for-byte — rows exist, so data exists, whatever the connector tables say (this is what keeps a
seeded or manually-loaded ledger answering exactly as before, exit gate c).

**Scope 3 found two more of the same shape**, neither in the original row:

- `opt_out_count` — *"0 customers are excluded from your campaigns"* against an empty ledger reads as
  a FINDING (nobody has opted out) when the truth is nobody is loaded.
- `customer_list` — sent an EMPTY CSV and announced *"I've sent your customer list"*. That is this
  row's fabrication with a file attached to it: the owner opens a document asserting their business
  has no customers.

`last_campaign` and `billing` are shown SAFE rather than guarded: a campaign we did or did not run is
a claim about OUR records, true whatever the owner has connected. The full enumeration lives in
`test_every_aggregate_branch_states_its_precondition` so it cannot silently rot.
