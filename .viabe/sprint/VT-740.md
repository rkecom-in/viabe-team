# VT-740 — an automatic re-drive that never asks what already went out

## The hazard, verified three ways

`orphan_reaper.reap_stalled_manager_tasks`'s VT-560 wake:

```sql
UPDATE manager_tasks SET status = 'planned', next_retry_at = NULL, ...
 WHERE status = 'blocked' AND next_retry_at IS NOT NULL AND next_retry_at <= now()
```

1. **Effect-blind.** The predicate reads status, nullity and time. It never consults the send
   ledger. A workflow that messaged 40 of 100 customers and died is re-driven on exactly the same
   terms as one that sent nothing.
2. **Hourly, steady state.** `ORPHAN_RUN_REAPER_CRON = "0 * * * *"`, registered at
   `scheduled_triggers.py:1500`. Not boot-only.
3. **Already on `main`.** `git show origin/main:…/orphan_reaper.py` carries the same block. This is
   not a promotion risk to be caught in the package — it is live prod code.

**Send idempotency does not cover it.** `idempotency_key = f"agent:{draft_id}"`
(`agents/customer_send.py`) is keyed to the DRAFT, and a re-drive re-runs the specialist, which
mints new drafts and therefore new keys. **No per-customer cooldown exists** — the
`idx_send_idem_tenant_customer_created` index was created for one and nothing queries it.

It has cost us nothing so far only because no real customer send has been authorised. **That is a
policy holding the line, not a mechanism.**

## Why my first fix was reverted — read this before writing the second

I added `AND NOT EXISTS (… campaign_messages m WHERE m.campaign_id = c.id …)`. Adversarial review
killed it, correctly:

**`campaign_messages.campaign_id` is never populated.** The sole writer
(`send_whatsapp_template._write_campaign_message`) omits the column; there is no `UPDATE
campaign_messages` anywhere. So that join matches zero rows for every campaign, real sends
included — **the gate was inert.** This repo already documents the trap, on
`has_approved_campaign_with_no_messages` (`db/wrappers/__init__.py`): *"joining on it would find
zero rows for EVERY campaign, real sends included."* I wrote the broken join anyway, twice.

Worse than inert: `effect_state_rollup` and `prod_workflow_diagnosis` carried the same join, so
every finding would have rendered **"SAFE TO CANCEL — nothing reached a customer"**, including a
campaign that messaged 40 real people. That half is fixed and pushed (`9ae4e416`): the join now
uses the documented `{campaign_id}:{customer_id}` idempotency prefix, and — because that prefix
does **not** cover the agent draft-send path — a zero delivered-count with unattributable sends
present now classifies as **`unknown`**, not `no_effect`.

## What a correct containment has to solve

1. **A trustworthy task→campaign link.** There is none today: `manager_tasks.source_message_ref`
   is a nullable TEXT pointer holding either a run_id or a message_sid. **The real fix is to
   populate `campaign_messages.campaign_id` at write time** — that makes the effect join exact
   everywhere and retires the prefix-matching workaround. It is a change to the send path, which
   is why it is a rostered row and not a late-night patch.
2. **Two send-key formats.** `campaign/execute.py` D1 uses `{campaign_id}:{customer_id}`;
   `agents/customer_send.py` uses `agent:{draft_id}`. Any join-based approach must cover both or
   declare what it cannot see (which is what `unknown` now does).
3. **A SECOND automatic path out of `blocked`.** `approval_resume.py` calls `redrive_task` when an
   owner replies yes to a `campaign_send` bound to a blocked/dead-lettered task — inbound WhatsApp,
   money path, no effect check. **Gating only the reaper leaves this open**, so a fix that covers
   just the sweep is not a fix.
4. **The withhold must be BOUNDED.** `blocked` is in `TASK_ACTIVE`, so it holds the tenant's active
   slot, and `settle_unretryable_block` CASes on `next_retry_at IS NULL` — which a withheld task
   never has. Withholding without a ceiling re-creates the VT-736 wedge that was closed days ago.
   Either let the ladder reach `dead_letter` (terminal, releases the slot, alerts) or add an
   explicit age ceiling.
5. **Withheld tasks must be ALERTED, not logged.** A withheld task needs a human. The sibling
   detectors in that file (`_alert_orphaned_tasks`, `_alert_dead_letter_tasks`) write
   `tenant_alerts` → Ops Console + Telegram; a `logger.warning` is pull-only and nobody is paged by
   it. Containment nobody can see is a slower silent failure.

## Boundaries

- **Fail-closed:** unreadable effect-state means DO NOT WAKE. Never "wake anyway."
- **No blind re-run, no silent disable** on a partial send (Fazal 2026-07-10, binding).
- The system CONTAINS + DIAGNOSES + REPORTS. **The VTR takes the action.** No silent auto-resolution
  of an effectful failure.
- Any re-run that would re-send needs the same approval + idempotency guarantees as an original.

## Exit gate

(a) `campaign_messages.campaign_id` is populated by every send path, proven by a real send on dev.
(b) A partially-delivered task is demonstrably NOT woken — proven by forcing the state, not by
reading the SQL. (c) The `approval_resume.redrive_task` path is gated the same way. (d) A withheld
task raises a `tenant_alerts` row and cannot hold a slot indefinitely. (e) The diagnosis is wired to
a surface a VTR actually reads.
