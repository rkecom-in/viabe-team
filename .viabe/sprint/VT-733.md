## Verify-first answers (CC, deployed dev, 2026-08-05 — measured, not assumed)

**0. SCHEMA FACT found by a failing clean-apply, not by reading:** `tenant_llm_limits` has **no
`max_cost_usd_day`** — per-tenant ceilings are **monthly only** (`max_cost_usd_month`,
`max_tokens_in_month`, `max_tokens_out_month`); the DAILY ceiling exists only on
`global_llm_limits`, platform-wide. My first cut of mig 192 coalesced a tenant day cap that cannot
exist; the pre-push migration test caught it on clean apply. Fazal's Q2 ("what default tenant cap
ships at launch") therefore has a constrained answer: a per-tenant DAILY cap would need a schema
change, not just a value.
Also unused by the console today: the per-tenant TOKEN ceilings — a second lever that exists and is
not surfaced.

**1. Default caps: NONE are in effect.** `global_llm_limits` holds exactly one row —
`enabled=true, soft_pct=80`, but **`max_cost_usd_day` and `max_cost_usd_month` are both NULL**.
`tenant_llm_limits`: **0 rows**. So the enforcement half is wired and switched on while configured to
no limit: `budget_gate` can never return a hard verdict today. Clau's suspicion confirmed, and it
sharpens Fazal's Q2 — the question is not "what should the default be" in the abstract but "we ship
with no ceiling at all unless you set one."

**2. The VTR-vs-VTAdmin write distinction is INTENT ONLY *in the database* — refined below.**
CORRECTION to how I first put this to Clau ("slice A must BUILD the distinction"): the role
machinery DOES exist, in the WEB layer (`requireOpsOperator` + `assignedTenants`, what the
run-replay cluster scopes on). What does not exist is any DB-level write boundary. So slice A WIRES
cap writes into the existing web gate — it neither invents a role system nor pretends the database
enforces one.
Both caps tables have `rls_on = true, rls_forced = true`, and their ONLY policies are `SELECT` for
`{public}`. There is **no INSERT/UPDATE/DELETE policy at all**, so every write is denied under RLS
regardless of role — the effective rule is "only a BYPASSRLS/owner connection may write", with no
VTR-vs-VTAdmin distinction anywhere. `budget_gate.py`'s "only VTR admin can set/control limits" is a
docstring claim, not an enforced boundary. **Slice A must therefore BUILD that distinction, not
surface it.**
Second-order: `anon` and `authenticated` hold table-level INSERT/UPDATE/DELETE grants on
`tenant_llm_limits`. They are inert while no write policy exists — but they are a loaded gun for the
day someone adds a permissive write policy. Revoke them as part of slice A.

**3. Luna's rates ARE in the registry** — `model_pricing` prices all 13 supported models. Relevant
numbers for the repricing brief (USD per Mtok, in/out): `gpt-5.6-luna` **1.00 / 6.00** ·
`claude-sonnet-5` **2.00 / 10.00** · `claude-opus-4-8` **5.00 / 25.00** · `claude-haiku-4-5`
1.00 / 5.00 · `glm-5.2` 1.40 / 4.40 · `grok-4.3` 1.25 / 2.50. So the VT-732 Sonnet burn was running
the product at ~2× input and ~1.7× output cost versus the tier it was supposed to be on.

## Slice A — BUILT 2026-08-06 (committed; deploy held behind the pack's push window)

- **mig 192** — `ops_tenant_cost_summary` (per tenant × agent × model) + `ops_tenant_cap_status`
  (spend vs cap over the cap's OWN window, so a percentage means what it says). Aggregation in
  Postgres like the sibling ops RPCs; `service_role` EXECUTE only, never PostgREST-public.
- **mig 192 also revokes** the `anon` / `authenticated` INSERT/UPDATE/DELETE grants on both caps
  tables — inert today only because no write policy exists, live the day someone adds one.
- **`lib/ops/cost-access.ts`** — `hasFullCostAccess` / `canEditCaps` / `canEditPlatformCaps` /
  `scopeCostTenantFilter` / `capUtilisation`. A VTR SEES its tenants' spend but cannot lift a
  ceiling: the operator closest to a tenant is the one most likely to be asked to lift it "just for
  today". An out-of-scope request 403s rather than silently narrowing — a console that quietly shows
  less than the operator believes is worse than one that errors.
- **`GET /api/ops/cost`** — role-split like the run-replay cluster; the tenant set is derived from
  the operator's assignment, never from the client (IDOR, caught twice).
- **`/team/ops/cost` page** — spend by tenant and agent, with the uncapped count in the header.
- **`capUtilisation` returns null, never 0, when no ceiling exists.** A missing cap and an unused cap
  look identical on a progress bar and only one means "can spend without limit". Today that is EVERY
  tenant, so the page renders "no cap set" in amber rather than a comfortable 0%.

12 vitest cases (`tests/lib/ops-cost-access.test.ts`); tsc + eslint clean.
**Not yet deployed:** `run_critical_x3 --resume` refuses to merge segments across an app-version
change, so no deploy may land until the ×3 gate finishes.

## Slice B — NON-LLM METERS (the invisible half of tenant cost)
Same one-row-per-event ledger pattern, new `integration_cost_events` (or extend the ledger with a
`kind`): **Twilio** per-message (template vs session rates) · **Voyage** embeddings ·
**Sarvam** ASR seconds · **Apify** actor runs · **ScrapingBee** requests. Rate table
config-driven (rates change; a hardcoded rate is the model-literal mistake wearing a price tag).
Where a vendor bills per-unit-opaque, record units + best-known rate and mark estimated.

## Slice B — STARTED 2026-08-06 (ledger + rates + two call sites wired)

- **mig 193 `integration_cost_events`** — shaped like `llm_call_events`, RLS forced, tenant-scoped
  read, no write policy and no anon/authenticated grants (the loaded-gun class slice A had to revoke
  is never created here).
- **`config/integration_rates.yaml`** — rates as CONFIG. Every row persists the rate it USED, so a
  later edit cannot rewrite history.
- **`integrations/cost_meter.record_integration_cost`** — mirrors `record_llm_call`; fail-soft
  (CL-122: the vendor call already spent the money). An unknown vendor/unit records the QUANTITY at
  zero cost flagged estimated — inventing a rate would put a fabricated number into the repricing
  input, and the flag is what stops that zero reading as "free". 8 tests.
- **WIRED: Twilio template sends** (after a confirmed send; `external_ref` = the message SID so a
  month reconciles against the invoice) and **Sarvam ASR** (seconds DERIVED from payload size,
  therefore flagged estimated).

**NOT yet wired, and why it is not a one-liner:** Voyage (`knowledge.embeddings.embed_texts`), Apify
(`methods.apify_client.run_actor`) and ScrapingBee (`methods.knowyourgst`) have **no tenant_id in
scope** at their call seams. Metering them platform-level is easy and nearly useless — the row's
question is "what does THIS tenant cost". Per-tenant attribution needs tenant_id threaded to those
three seams, which is a real change to their signatures and callers. Doing it half-way (a
platform-level row that looks like coverage) is the failure mode this row exists to avoid, so it is
called out rather than quietly shipped.

- Cost-per-journey attribution where the journey id exists on the run.
- After ONE WEEK of Luna-era packs incl. a dirty cycle: a measured **cost-per-tenant-month
  distribution** handed to Fazal as the repricing brief. NO pricing recommendation from
  estimates — measured numbers only. (Fazal 2026-08-05: ₹5000/agent may be high; the rework
  waits for this number.)
- **ATTRIBUTED GROSS PROFIT PER TENANT — first-class (Fazal-ratified 2026-08-06).** The console
  shows BOTH halves per tenant: what the tenant costs us AND what we made them — recovered-order
  value from SR outcomes (the §7C impact-judge + money-truth ledger substrate), attributed
  conservatively (DB-provable orders only, never inferred). This is pilot proof bar **P3**
  (launch-tracker Pilot Proof Gate) and the sales pitch itself: "generated ₹X attributable gross
  profit, charged ₹Y." Attribution rules err UNDER, never over — an inflated attribution number
  discovered by an owner destroys exactly the trust it exists to build.
