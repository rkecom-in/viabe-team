# VT-763 — the specialist says "no data" on a tenant that has data

## Measured

Six SR scenarios were CCC in gate (d) (18/18) and flip in the M2 pack. Re-driven ×3 on the VT-762 build
(so NOT the triage truncation, which is fixed and probed 0/24): **r1 3/6 · r2 0/6 · r3 5/6.** Same shape
every time — the owner gets VT-755's honest ask instead of a draft:

```
I can't build this yet — something I need from your data is missing, and I'd rather ask than guess.
```

When it works, the same scenarios draft 3–6 customers normally.

## The kept tenant, read directly (79dd617f, `sr_winback_plan_hinglish`, r-keep)

| fact | value |
|---|---|
| tenant | `owner_inputs=TRUE`, gstin_verified, trial |
| customers / sales / consents | 5 / 5 (`sale`, Feb–Aug) / 5 (0 opted out) |
| connector | `google_sheet` enabled + `last_status=ok` (this is why VT-755's ask picks the "all present" sentence) |
| seam | `campaign_first_contact_dispatched: win-back imperative + real cohort — deterministic sales_recovery dispatch` |
| loop | `workflow_picked_up` at **2.8s**, `specialist_dispatch` at **8.7s** (VT-752's first live numbers — the handoff is NOT the slow part) |
| specialist | `campaign_plan_emitted variant=insufficient_data`, `missing_data[0].category="evidence"`, remediation *"Provide a registered customer-ledger or campaign-context tool result, or retrieve…"* |
| review | `needs_owner_input → ask_owner`, question delivered, task `waiting_owner`, no campaign |

So: **the seam saw a real cohort; the specialist claimed to have no evidence.** The SR agent has `tools=[]`
— its cohort arrives via `context.dormant_cohort` (`context_builder._build_dormant_cohort`). Either that
came up empty on the specialist's context build (a different call from the seam's cohort check), or the
model had the cohort and refused to plan without a "tool result" to cite (its own words).

**And that is exactly the fact I could not read.** The empty-cohort WARNING did not fire for this tenant;
the built-cohort line is INFO, and the deployed log stream carries WARNING+ only; the consent-gate return
was silent. VT-755 scope 4 instrumented the count for precisely this question and it was invisible.

## Built (this row, step 1)

`_audit_cohort` — every branch of `_build_dormant_cohort` (`consent_gate_closed` / `consent_check_failed` /
`built` with counts) now writes a durable `tm_audit` row, counts only (CL-390). Next: deploy, ×4 with
`--keep-tenants`, read the row for the failing runs. That splits the two hypotheses in one look.

## Ruled out so far

- Triage truncation (VT-762) — probed 0/24 after the floor.
- The VT-757 ordering — D3/option-C route to the SAME deterministic dispatch; the kept tenant's audit shows
  it dispatched with a real cohort.
- Tenant state — complete on the kept tenant.
- `HardLimitExceeded` in the log window — see VT-764; fires on every brain run and is swallowed, so it is
  noise here, not the mechanism.

## Not ruled out

- A time-varying model behaviour (sonnet-5 adaptive thinking; the failures cluster by the hour).
- The specialist's context build returning an empty cohort intermittently (the RV-1 flake `review.py` names).
- Something in the batch that widened either. VT-762's floor did not touch the SR per-turn cap (4096).
