# VT-745 — mint the customer hook link, or the clicked tier is fiction

## The defect

`integrations/hook_links.py::mint_customer_hook_link` is the sole INSERT into
`customer_hook_links`. **Nothing calls it.** An exhaustive grep across `*.py` / `*.ts` / `*.tsx` /
`*.sql` outside tests returns the definition, its `__all__` entry, and docstrings — nothing else.
The only mint surface, `api/hook_links.py` `POST /api/orchestrator/hooks/mint`, takes
`{tenant_id, source}` and calls the non-customer `mint_hook_link`; there is no customer variant and
no `customer_id` in the body. team-web has no caller either.

So the table is empty in production, forever, and `send_frequency._ENGAGEMENT_SQL`'s
`clicked_age_s` sub-select returns NULL on every call.

## What that does to the ratified rule

| Fazal's rule | What actually evaluates |
|---|---|
| Tier A — replied **or clicked** within 30d | replied within 30d |
| Tier B — read **or clicked** or replied within 90d | read or replied within 90d |

**The degradation is SAFE and that is exactly why it is dangerous.** A missing signal can only push
a customer toward Tier C — the longest interval, the most suppression — so nothing errors, nothing
alerts, and no test fails. It simply is not the rule that was ratified, and any later analysis of
tier distribution would be measuring two signals while believing it measured three.

## RULING LANDED — D-B, Fazal 2026-08-15 — and HIS CHALLENGE CORRECTED MY ANALYSIS

I closed this row as *"the clicked signal is UNOBTAINABLE through any channel this product has"*, resting on
two findings: no customer template carries a URL variable, and free-form needs an open 24h window that a
lapsed win-back target does not have.

**Fazal's question — "isn't that exchange inside the 24h window?" — is the half I got wrong.** My analysis
collapsed two different cases into one:

| case | 24h window | can a tracked link go out TODAY? |
|---|---|---|
| cold win-back to a LAPSED customer | closed by definition | **no** — needs a URL-button template |
| an IN-SESSION exchange (the customer has messaged us) | **open** | **YES** — free-form, no template needed |

I asserted the first and generalised it to "any channel", which was too absolute. **In-session links need no
template and are capturable immediately.** So the signal was never unobtainable — it was unobtainable *for
the cold-outreach case I happened to be looking at*.

**The ruling, three parts:**
1. **Build the click infrastructure NOW.** In-session links need no template, so `customer_hook_links` can
   have a real writer today. This is no longer decision-blocked.
2. **Amend the tier rule** to the two live signals, with `clicked` counting **whenever observed** but never
   a precondition. So the rule stops claiming three signals it cannot always get, and starts counting the
   third the moment it appears.
3. **The URL-button template variant is Fazal-side at leisure**, off the critical path.

**Scope SHRANK: infra + rule amendment, no template dependency.** The tier-discriminating case
(clicked-but-not-replied on a cold send) arrives when the template does — so **design the read to start
counting on its own**, with no code change needed at that point.

**Status change:** this row moves from CLOSED-AS-INVESTIGATED back to BUILDABLE, and it is now coupled to
VT-754: D-C makes a tracked-link click one of only two things that count as attribution, so this
infrastructure is load-bearing for revenue, not just for a frequency tier.

**Note on my own honesty test:** `test_vt745_click_signal_honesty.py` asserts the shortfall note keeps the
word "unobtainable". That word is now wrong. The test's AUTO-RED trigger on a production mint caller will
fire the moment the infra lands — which is correct behaviour — and the note must be rewritten to say what is
actually true: obtainable in-session, not obtainable for cold sends until a URL template exists.

## Scope

1. **Mint a customer hook link wherever a customer-facing link goes out** — the campaign send path
   and the agent draft-send path both compose customer copy. Use the existing
   `mint_customer_hook_link`; do NOT write a second mint.
2. **The existing constraints are already correct and must survive**: the token IS the capability
   (no customer / tenant / campaign id and no phone in the URL, resolved server-side), the table
   carries its own RLS + FORCE (a customer-attributed click is a different privacy class from
   `hook_links`' deny-all no-PII posture), and it is registered in `_PURGE_ORDER` — verify that
   registration still holds after any change.
3. **Delete the shortfall note** in `send_frequency.py`'s `_ENGAGEMENT_SQL` docstring when the mint
   lands. A note describing a gap that no longer exists is the next stale-status defect.

## Boundaries

- A link mint must never gate or delay a send. If minting fails, the message still goes; the click
  signal is advisory and its absence is already handled (NULL → no signal → Tier C direction).
- No customer id, tenant id, campaign id or phone in any URL. Enumerable or forgeable tokens are a
  customer-data leak, not a tracking gap.
- Clicks are engagement, never consent and never authorization. A click must not be readable as an
  opt-in.

## Exit gate

(a) A real customer send on dev produces a `customer_hook_links` row. (b) A resolved click stamps
`last_clicked_at`, proven end-to-end, not by reading the recorder. (c) A customer who clicked and
did not reply reaches Tier A — i.e. the signal actually changes the tier, which is the only proof
the wiring did anything. (d) `_PURGE_ORDER` still contains the table.

## Why this row exists at all

**Fifth instance this week of built-exported-and-called-by-nothing** — after the O8 retrieval engine
(`retrieve_cards_for_turn`, zero callers), `prod_workflow_diagnosis` (finished, no route, no
schedule), and two wake gates that were live but inert. Each was caught only by someone tracing the
production call path rather than trusting that a merged function runs. That trace is now the first
question of any verification here, and it is the reason this was caught before landing rather than
after.

## BUILT / NOT BUILT 2026-08-15, and a third finding that changes part 1

**D-B part 2 — DONE, and it needed no code.** `clicked` was already one signal among several in a
FIRST-MATCH tier test: the SQL selects `clicked_age_s` unconditionally and `TierSpec.matches` treats a
NULL as simply not matching, so the read starts counting the moment a click lands, with no code change
— exactly what the ruling asked for. "Needs no change" is the kind of claim that quietly stops being
true, so it is now pinned behaviourally: click-alone → Tier A, reply-alone → Tier A (clicked is not a
precondition), click at 60d → Tier B, nothing → Tier C.

**D-B part 1 — NOT BUILT, deliberately, and this is the deviation to review.** The ruling's premise is
right: an in-session exchange has an open 24h window, so a free-form message needs no template and
could carry a tracked link today. Building a mint caller on top of that still fails, for a reason
neither of us had:

**No production surface composes a customer-facing link at all.** Checked, not reasoned about:

- both customer send paths (`customer_send.agent_send_draft`, the campaign executor) send TEMPLATES;
- the in-session replies in `integrations.customer_inbound` are three FIXED sentences ("You've been
  opted out…", "Thanks — you're opted in…", "Thanks for your message — the team will get back to you
  shortly.") with no link and no composition step;
- `/r/<token>` is an EMAIL/SMS acquisition primitive (`integrations/hook_channels.py`, VT-288) meant to
  pull someone from OUTSIDE WhatsApp into a chat — and **nothing calls those channel functions
  either**.

So the in-session capability is real and unused. Wiring a mint today would mean inventing a link to
send, and it would be the **sixth** built-exported-and-called-by-nothing this fortnight — the exact
defect class this row exists to prevent. I judged that the wrong trade and stopped, per the standing
"build the closest thing honouring the INTENT, record the deviation, flag it" instruction.

**What the intent needs instead** (Fazal's call, not mine): a customer-facing link worth sending. The
two candidates are the URL-button win-back template (already D-B part 3, Fazal-side) and wiring the
VT-288 email/SMS hook outreach. Either one gives the mint an honest caller; until then the
infrastructure — mint, click recorder, RLS + FORCE, `_PURGE_ORDER` registration — is complete and
waiting, and the tier read will start counting on its own.

**The word "unobtainable" is retracted** from `send_frequency.py`'s note and from the honesty test, per
D-B. The replacement is narrower and less flattering: not "no channel can carry it" but "no feature
sends one". Both AUTO-RED triggers survive unchanged (a production mint caller, or a customer template
gaining a link variable), and the note's evidence tokens moved with the claim so a future reader still
cannot re-roster "just wire the mint" without hitting the reason it does not work.

still contains `customer_hook_links`, re-verified. (e) ✅ NEW: the tier rule counts `clicked` whenever
