# VT-753 — the assertion is sound in shape and wrong in budget

## Clau asked which of two causes it was. Neither — here is the actual one.

The hypothesis was that `4331128e` either did not cover this path, or that settling stops before
terminal. **The fix IS in place and it DOES cover `assert_route`** —
`canaries/convo_harness.py:1828-1844` puts `assert_route` in the settle list, with the comment
recording exactly why it was added.

The defect is the **budget**:

| deadline | value | file |
|---|---|---|
| harness DB-assert settle | **150s** | `convo_harness.py:1685` `_DB_ASSERT_SETTLE_S` |
| harness step timeout | 180s | `run_full_pack.py` default `--timeout` |
| product in-turn D1 wait | ~96s | `runner.py` `_D1_INTURN_WAIT_MAX_POLLS = 24` × 4s |
| **measured work** | **~390s** | VT-752, three cases: 382 / 416 / 373s |

**Every deadline in the system is calibrated below the real chain.** So the settle loop expires,
`assert_route` reads "no campaigns row", and reports `expected delegation … observed route='none'` —
a ROUTING verdict derived from a LATENCY fact. In S1 pass 1 that verdict was **FALSE for 3 of the 4
scenarios it flagged**: all three had a `campaigns` row minutes later, `status=proposed`, task
`waiting_owner`, nothing sent.

## Why this is Critical rather than a harness nit

It is a **measurement-integrity** defect, and measurement is how every other decision gets made:

- The retracted **24% / 33% / 40%** figures are very likely this artifact, not a routing defect.
- The numbers quoted in `GO-LIVE-BLOCKERS.md` **B1** and the promotion package inherit it. **Clau owns
  that re-audit** (its 0500Z signal) once the window closes.
- **Any gate (c) number I report today carries the same flaw**, which is why S1's result is being
  reported in the A/B/C/D buckets with the DB settled per run, not as a single blended rate.
- VT-738's own root-cause section already had to retract a premise once for this class. Twice is a
  pattern, and the pattern is *asserting product intent from a snapshot*.

## Scope

1. **An assertion may claim a routing verdict ONLY after the turn reaches terminal.** Anything
   earlier labels itself a LATENCY assertion and is reported in a separate bucket. Clau's exit-gate
   wording, adopted verbatim.
2. **Settle to terminal, not to a clock** — poll the task/workflow state to a terminal status
   (`completed` / `failed` / `waiting_owner` / `dead_letter`) rather than expiring on 150s. A budget
   is the wrong primitive: it encodes an assumption about latency that VT-752 shows is 4× stale.
   Keep a hard ceiling far above the measured chain purely as a hang-stop, and make expiry at the
   ceiling report as `INDETERMINATE`, never as a routing failure.
3. **Never let a DB-snapshot proxy produce a behavioural verdict.** `assert_route`'s route signal is
   the campaigns-row-existence proxy (`convo_harness.py:442,473` already flag the proxy as needing
   re-grounding). Either ground it in a real recorded route column or state in the failure text that
   it is a proxy.
4. **Re-run S1 pass 1 after the fix** and publish the delta: how many of the 6 non-clean runs were
   routing, how many latency. That delta IS the size of the historical error.
5. Ceiling and budget constants get a comment stating the MEASURED chain latency they are calibrated
   against, and the date — the T9 comment claiming "~30-60s" is how a stale budget survived.

## Relationship

**VT-752** is the product-side defect (the chain takes ~390s; the ack is content-free; the promise has
no handler). **This row is the measurement-side defect** — the same 4× staleness expressed in the
harness's budget instead of the runner's. They must land in this order: until this one is fixed, the
fix for VT-752 cannot be measured, because the instrument reports latency as routing.
