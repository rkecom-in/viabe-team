# VT-736 — release the slot

## The defect
Every `_block_*` path (`manager/workflow.py:446/473`, plus manager_review's escalate) sets
`status='blocked'` + `terminal_outcome='escalated'` and arms **no `next_retry_at`**. Then:

1. `blocked` ∈ `TASK_ACTIVE` (`task_store.py:44`) → the row **holds the tenant's one active slot**.
2. `workflow.py` promoted the queue only `if final_status in TASK_TERMINAL`, and **`blocked` is not
   terminal** → every task queued behind it starved.
3. `orphan_reaper.py:189-199` wakes `blocked` rows with an elapsed `next_retry_at`; one **without**
   is, in the code's own words, *"left for a human."*

**Effect:** the tenant can still chat — the turn-brain answers — but **no task of any kind ever
executes for them again**, and `dispatch.py:593` keeps injecting *"You already have a task in-flight
… do NOT start a duplicate"*, so the manager tells them work is "already in progress". Silent,
permanent, invisible to the owner, and it looks like the product working.

**Found live on dev:** 5 tenants holding a wedged slot — 3 via the `escalated` closure path, oldest
**a month old**, newest 9 days. Not a rare race: the entry is the ordinary honest-failure closure.

## The fix
`task_store.settle_unretryable_block()` settles such a task to **`dead_letter`**, called from the
workflow tail after the owner notify. `dead_letter` is what the status already means here —
documented in `task_store.py:36-37` as *terminal (retry budget spent) but OPERATOR-REDRIVABLE; the
reaper never auto-retries it*. Settling there releases the slot, lets `_promote_next_queued` fire
(it is terminal), and keeps ops visibility + redrive.

Rejected alternatives, and why: flipping `blocked` out of `TASK_ACTIVE` would change the meaning of
the mig-165 partial unique index that enforces one-active-task; a NEW status would lose
`redrive_task` support, which already accepts `dead_letter`.

**`next_retry_at IS NULL` lives INSIDE the UPDATE**, not a read-then-write: the reaper may arm a
retry concurrently, and a task awaiting retry is not wedged and must not be settled. That is the one
way this fix could have caused damage, and it has its own test.

## Proven
- **8 new DB-backed tests** (`test_vt736_wedge_slot_release.py`): settlement, **slot actually freed**
  (`has_active_task` True→False), retry-pending NOT settled, idempotent, running task untouched,
  `terminal_outcome` preserved, still redrivable, and **a queued sibling promoted after the wedge
  clears** — with a precondition assert that promotion returns `None` *before* the fix. That last one
  turns the starvation half from "mechanically implied" into observed.
- **The 5 live dev tenants settled** through the shipped wrapper: every one `slot_active: True →
  False`; **0 wedged rows remain on dev**. None had queued tasks behind them, so promotion had
  nothing to fire there — the test covers that half, and this is stated rather than glossed.
- **An existing test encoded the wedge as an invariant** —
  `test_blocked_outcome_does_not_promote_a_queued_sibling` asserted the sibling stays queued. Its
  rationale was circular (restating that non-terminal doesn't promote, never why a task that can
  never resume should keep the slot). Rewritten as
  `test_escalated_block_releases_the_slot_and_promotes_the_queued_sibling`, plus a NEW
  `test_a_block_awaiting_retry_keeps_the_slot` preserving the half of the old invariant that was
  right. 14 sibling assertions moved to a `_PERMANENT_BLOCK` constant that documents the change once.
- `test_workflow.py` 32 passed (was 16 passed / 15 failed).
