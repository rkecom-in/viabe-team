## Two real defects in one trace (a third was my error — retracted below)

1. **An approval was resolved by an inbound that PREDATES it.** The decision path consumed a message
   that arrived before `requested_at`. Ordering is not checked, so a stale inbound can satisfy a
   future approval. (Suspected surface: the VT-633 D-A approval-arm wait — a "clear owner decision
   that lands while the loop is still arming" — reaching backwards to a message that was never a
   decision.)
2. **The consumed message was not consent in any reading.** "bhej do abhi" is the ASK. Treating the
   owner's impatient repeat as approval of a plan they had not yet seen inverts the gate: the louder
   the owner asks, the faster the system self-authorises. The canary's step 2 ("jaldi karo yaar,
   sabko ek saath bhej do, wait mat karo") exists precisely to catch this.
3. ~~**A fabricated completion claim**~~ — **RETRACTED, my error.** I first reported "sent it to 19
   customers with ZERO campaign_messages" as a third defect. It is not one: there ARE 19
   `campaign_messages` rows. My verification query joined `campaign_messages.campaign_id`, and the
   send path deliberately never writes that column — `CampaignsWrapper.executed_campaign_exists_for_
   runs` says so in its own docstring ("the campaign_id column is never written by the send path")
   and joins on the `{campaign_id}:{customer_id}` idempotency-key prefix instead. The composer
   (`campaign_outcome.compose_campaign_outcome_message`) is honest by construction: `sent > 0` →
   "gone out", else "I couldn't send it to any customers". **The manager told the truth.**
   This makes the finding WORSE, not better: the send was not a phantom — 19 customers were really
   messaged on an approval the owner never gave.

The mechanism is the approval-decision path, not the VT-732 model seam: the resolution is keyed on an
`owner_message_sid`, which has nothing to do with which model answered. VT-732 is not exonerated by

## Fix — BUILT 2026-08-06 against Fazal's ruling (CL-2026-08-06-repeated-request-is-never-approval)

Both halves, conjunctive, as ruled:

**(1) Ordering invariant at the single resolution choke point** —
`approval_resume._assert_decision_is_newer_than_the_ask`, called from `mark_approval_resolved`, so it
covers every owner-decision path (deterministic, shadow and enforce modes alike) rather than patching
`campaign_send`. The resolving inbound must be strictly newer than
`COALESCE(presented_at, requested_at)`. `presented_at` is new (mig 190), written by
`start_decision_clock` — the same idempotent write that starts the decision clock at DELIVERY, so
presentation time and clock start can never disagree. Fails CLOSED on an unknown boundary or unknown
message time. `owner_message_at=None` (timeout sweep, supersede) skips it by design: those are not
owner decisions. The runner reads the inbound's real `twilio_inbound_events.received_at`, NOT
wall-clock at resolution — the resolving turn can run a minute later, and that gap is exactly what is
being measured.

**(2) Content rule** — `approval_resume.is_repeat_of_request`, checked FIRST in
`resolve_decision_from_reply`, ahead of every classifier and mode. A reply whose meaningful tokens
add nothing to the original request is a re-ask, not consent. Deterministic token-set containment,
not similarity scoring: "haan bhej do" introduces `haan` (decision content the request lacked) and
still approves, protecting VT-615's bare-Hinglish approval; a verbatim re-send introduces nothing and
is refused. Rejections are never swallowed — a novel negation/reject token always reaches the
classifier.

Tests: `tests/orchestrator/agent/test_vt734_approval_ordering.py` — 12 cases pinned to the breach's
own timeline (including the exact 72-second inversion) and to the tokens involved.

## Original fix direction (superseded by the build above)
- **Hard ordering rule:** an approval may only be resolved by an inbound whose `created_at >
  requested_at`. A message that predates the request can never be its decision. This is deterministic
  and does not depend on the classifier.
- **Consent semantics:** a repeat of the original REQUEST is not approval. The approval classifier
  must distinguish "asking again" from "approving", and default to NOT-approved when unsure — the
  standing preference for None/re-confirm over deterministic approve on money paths.
