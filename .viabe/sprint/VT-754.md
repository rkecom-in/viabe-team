# VT-754 — a two-word vocabulary mismatch, and revenue attribution has been empty since VT-417

## The defect

`billing/attribution_writer.py:85` joins the campaign's recipients to the money ledger on:

```sql
AND cle.entry_type = 'payment'
```

**Every production producer of `customer_ledger_entries` writes `'sale'`:**

| producer | value | note |
|---|---|---|
| `integrations/ingest.py:185` | `'sale'` | *"a connector sale is a sale — full stop"* |
| `integrations/methods/upi_export.py:280` | `'sale'` | changed FROM `'payment'` by VT-417 PR-3 |
| `integrations/methods/_image_adapter.py:224` | `'sale'` | |
| `integrations/imported_transactions.py:67` | `'sale'` | the model DEFAULT |

`EntryType = Literal["sale", "payment"]` — so `'payment'` is legal and simply never written.

**Measured on deployed dev, 2026-08-14:**

```
customer_ledger_entries by entry_type :  sale 50  ·  payment 0
attributions rows                     :  18   (all 2026-05-06/05-26, customer_id NULL,
                                               attribution_method NULL — stale fixtures,
                                               not writer output from a real join)
campaigns attribution_close_at SET    :  1 of 34
```

Zero `'payment'` rows means the join **cannot match**, for any tenant, ever. Not "has not yet matched" — cannot.

## Why it was introduced, which is the part worth reading

VT-417 PR-3 changed UPI credits from `'payment'` to `'sale'` **on purpose**, and its comment explains why:

> *"a UPI credit (customer→owner) IS a sale (money received for goods/services). The Sales-Recovery
> detector counts ONLY `entry_type='sale'` (`db/wrappers _LAPSED_CANDIDATES_SQL`), so `'payment'` made
> every UPI sale invisible to win-back targeting."*

That change was **correct for Sales Recovery** and is not to be reverted — win-back targeting is the
live, revenue-bearing path. It silently emptied attribution, because two subsystems disagree on one
word and nothing asserted the disagreement. There is no test anywhere that asserts a NON-ZERO
attribution against realistic ledger data; every attribution test supplies its own `'payment'` rows,
so the suite is green and the production result is always zero.

**The class:** a shared enum where one subsystem's writer and another's reader disagree, with no test
spanning both. Identical in shape to VT-746 (a `TriggerKind` the Python declared and the CHECK
refused) — a declared vocabulary nobody cross-checks.

## The decision Fazal owns, before any code changes

`attribution_writer` should count the money that came in after a campaign. The question is what that
means in ledger terms, and it is a revenue-semantics call, not a refactor:

- **(A) Attribute on `'sale'`.** One-line predicate change; attribution starts working immediately with
  the data that already exists. Accepts that "money received" is the attributable event.
- **(B) Attribute on both `'sale'` and `'payment'`.** Safest if `'payment'` ever becomes meaningful
  (e.g. an invoice settled later, distinct from the sale that created it).
- **(C) Start writing `'payment'` somewhere real** and keep the predicate. Only right if sale and
  payment are genuinely different events we want to distinguish — which no current producer does.

CC's recommendation is **(B)**: it fixes the live gap without asserting that `'payment'` will never
mean anything, and it cannot make attribution *worse* than the current zero. But this is a claim about
what the business counts as attributed revenue, so it is Fazal's, and an owner-facing revenue number
that changes meaning is exactly the kind of thing to decide deliberately.

## RULING LANDED — D-C, Fazal 2026-08-15 (CL-2026-08-15-three-m2b-rulings)

**Attribution errs UNDER, never over.** Only two things count: a tracked link/code, or reply-then-purchase
inside a defined window. Nothing else.

**That answers my three options by rejecting all of them.** I framed the choice as (A) attribute on `'sale'`,
(B) accept both values, (C) start writing `'payment'` — and recommended (B). The ruling is narrower than any:
**a bare ledger `'sale'` in the window is NOT attribution**, because a shop's sales continue whether or not
we messaged anyone. Joining `campaign_recipients` to any sale in a 7-day window would credit the campaign
with revenue it did not cause. My (B) would have done exactly that, at scale, in an owner-facing number.
Recorded because the recommendation was wrong in an instructive way: I was solving "make the join match the
data" when the question was "what did we actually cause".

**Window value, mine to pick per the ruling: 7 days.** Consistent with the existing
`attribution_writer.ATTRIBUTION_WINDOW_DAYS = 7` and with `campaign_plan`'s own
`attribution_close_at == send_at + 7d` validator, so no new number enters the system and the close-at
validator stays true. Stated here as the row's decision of record.

**Revised scope, replacing the predicate-swap below:**
1. Attribution requires an ATTRIBUTABLE SIGNAL, not a coincident sale: a tracked link/code click, or an
   inbound reply followed by a purchase inside 7 days.
2. `entry_type` is therefore NOT the fix. The `'payment'` vs `'sale'` mismatch explains why the current
   writer produces zero, but correcting it to `'sale'` would produce a WRONG non-zero. Leave the predicate
   until an attributable signal exists to join on.
3. The click signal is VT-745's infrastructure (D-B: build it now). **These two rows are now coupled** —
   attribution's tracked-link half cannot exist before the click table has a writer.
4. Reply-then-purchase needs the reply attributable to a specific outbound, which VT-744's audit records as
   PARTIAL (`wa_conversations.last_inbound_at` is a mutable timestamp, not an event attributed to a message).
   That gap is now load-bearing for revenue, not just for observability.

## Scope (after the decision)

1. Apply the chosen predicate in `attribution_writer`, with the decision + date in the comment.
2. **A test that spans BOTH subsystems**: write a ledger row through the REAL producer path
   (`ingest` / `record_imported_transactions`), then assert attribution finds it. The existing tests
   insert `'payment'` by hand, which is precisely why they never caught this — a test that supplies the
   value under test proves nothing about the producer.
3. **A CI gate on the shared vocabulary**: any reader filtering `entry_type` must be reconcilable
   against the set of values producers actually write. VT-746 closed its analogous class by
   enumerating the Literal against the live CHECK; do the equivalent here.
4. Separately: nothing sets `campaigns.attribution_close_at` (1 of 34 rows on dev, and no writer in
   `src/`), so `_scan_attribution_close_eligible` finds ~nothing even before the join. The
   `campaign_plan` schema documents an `attribution_close_at == send_at + 7d` validator that no
   persistence path applies. Close that too or the fixed join still never runs on schedule.
5. Purge or clearly mark the 18 stale `attributions` rows on dev — they make the table look populated
   and are what made the audit's "CAPTURED" reading plausible.

## Boundaries

- **Do NOT revert VT-417 PR-3.** Sales-Recovery win-back targeting depends on UPI credits being
  `'sale'`; changing that back to fix attribution would break the live revenue path to fix a dead one.
- Do not backfill historical attribution. Inventing attributed revenue for past campaigns is
  fabricating a money number.
- Item 4 is a real dependency, not a nice-to-have: fixing the predicate alone leaves the sweep with
  nothing eligible to close.

## Exit gate

(a) A campaign whose recipients paid through the REAL producer path yields a non-zero `attributions`
row — proven end-to-end, not with hand-inserted `'payment'` rows. (b) The vocabulary gate fails if a
reader filters on an `entry_type` value no producer writes. (c) `attribution_close_at` is set by the
persistence path, so the daily sweep has eligible campaigns. (d) `.viabe/vt744-capture-audit.md`
field 3b reflects the corrected state (VT-748 owns the wording; this row owns the mechanism).

## BUILT 2026-08-15 — and scope 4 turned out to be a second, independent zero

**Scope 1, the join.** A qualifying row now needs an ATTRIBUTABLE SIGNAL that PRECEDES the purchase:
a `customer_hook_links` click (VT-745's table) or a `wa_conversations` reply, inside the 7-day window.
The `LATERAL` picks the stronger signal (tracked link over reply) and the purchase must fall at or
after it — a sale that precedes its "signal" is a coincidence with better timing, not a cause.

**Scope 2, entry_type.** The predicate is now `IN ('sale', 'payment')` — what producers actually
write, plus the grandfathered historical value. This is safe ONLY because the signal gate is in front
of it: the ruling's protection comes from requiring an act aimed at us, not from a predicate that
matches nothing. Leaving the mismatched predicate would not have been conservative, just broken.

**Method names, migration 206.** `window_match` cannot describe these rows — it means "this recipient
paid inside the window", which is precisely the inference D-C rejects. Writing honest matches under
that name would make them indistinguishable from the over-claiming ones in an owner-facing number.
Existing `window_match` rows keep their label: re-branding them would assert a signal never checked.

**The reply half needs the caller.** `wa_conversations` is keyed on a SALTED phone token and
`customers` is VT-72-watched, so the writer cannot derive it. `CustomersWrapper.recipient_phone_
tokens` computes it in the wrapper layer with the salt as a BOUND parameter (the pattern
`lapsed_candidates` and `agent_optout_attribution` already use), and `attribution_close` supplies it.
Any failure — unset salt, read error — degrades to the tracked-link half alone. Erring UNDER.

**Scope 4 was not a footnote — it was a SECOND independent zero.** Nothing in `src/` ever set
`campaigns.attribution_close_at` (1 of 34 rows on dev), and the sweep scans
`WHERE attribution_close_at IS NOT NULL AND <= now()`. So a perfectly correct join would still never
have run on schedule, and the number would have stayed zero for a reason that looks identical to the
first one from outside. `CampaignsWrapper.set_status` now arms it on the flip to `sent`, as
`send_at + ATTRIBUTION_WINDOW_DAYS` (the constant, imported — no second seven), `COALESCE`d so a
re-send or a status correction can never slide a running window forward.

**Scope 3, the CI gate.** `test_vt754_*` reads the accepted values out of the writer's SQL and the
written values out of every producer's INSERT site (by AST, not grep — the point is that a reader and
four producers disagreed for months and nothing could see it). A new producer value fails the build
and forces a deliberate reconciliation, the shape VT-746 used for its Literal-vs-CHECK drift.

**15 tests** (9 new + 6 existing rewritten). The rewrite matters: the old tests seeded
`entry_type='payment'` BY HAND and asserted it was attributed — they supplied the value under test,
which is exactly why they never caught that no producer writes it, and they asserted the over-claim
the ruling now forbids.

**This produces ZERO today and that is correct.** VT-745 records that nothing mints a customer hook
link yet, so the tracked-link half finds nothing; the reply half is live but only fires for recipients
who actually replied. The number will move when VT-745 gets a link-carrying surface.

**Scope 5 NOT done:** the 18 stale `attributions` rows on dev are untouched. They are `window_match`
rows from the old predicate and they make the table look populated — worth a deliberate cleanup, but
deleting rows on a shared dev environment is not something to do in passing. Flagged for the report.
