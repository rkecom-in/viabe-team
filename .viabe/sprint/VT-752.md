## The mechanism, file:line + causal chain

1. Owner asks for a campaign; triage starts an async `manager_task` for THIS turn
   (`skip_legacy_dispatch`) — that durable workflow OWNS the owner reply.
2. `runner.py` gives it a bounded head-start: `_D1_INTURN_WAIT_POLL_S = 4.0` ×
   `_D1_INTURN_WAIT_MAX_POLLS = 24` ≈ **96s** (`apps/team-orchestrator/src/orchestrator/runner.py`,
   the T9 inc-3 constants). The comment states the budget covers an *"observed spawn→SR→collapse→arm
   chain (~30-60s)"*.
3. **That premise is now false by ~4×.** The budget always exhausts.
4. D1 fires — `_COMPLETED_NO_REPLY_FALLBACK["en"] = "Got it — I'm on it and I'll update you
   shortly."` (`runner.py:161-164`, the VT-583 honest fallback).
5. The real draft + approval request lands ~5 minutes later, on a LATER turn — or never.
6. Anything asserting at that moment reads "no campaigns row" and calls it a routing failure.

Transcript, `sr_consequential_bulk_send_requires_approval`:

**So it is not one slow model call — it is rejection-and-retry.** A schema rejection 208s in, then a

That reframes the fix: the first question is not "why is the chain slow" but **"why is the model
emitting output that fails schema validation on the SR draft path, and why does a rejection cost
~200s"**.

## CORRECTION 2026-08-14 (CC) — I chased that reframe and BOTH halves of it were wrong

Investigated after VT-753 fixed the instrument, and re-measured on a fresh dev re-drive of the same
scenario (tenant `f92a09a9`, 637s). Two claims above do not survive, and item 0 is **not** the lever.

### (a) The rejection does NOT cost ~200s. It costs 11-18s.

The `schema_rejection` FailureRecord carries the SR agent's own elapsed time. Both of today's
rejections, live during the re-drive:

```
12:16:56  post-coerce CampaignPlan schema rejection: proposed.evidence_refs: too_short  wallclock_ms=11426
12:02:51  post-coerce CampaignPlan schema rejection: proposed.evidence_refs: too_short  wallclock_ms=18445
```

The `+208s` in the table above is the interval from `webhook_received` to the moment the error step was
**written**, not the cost of the rejection. Attributing that whole gap to the rejection was a mistake in
this row and it would have sent the fix at the wrong target.

### (b) The rejection is not a defect at all — it is the honesty gate WORKING

100% of schema rejections are the same single field: **`proposed.evidence_refs: too_short`**. That field
is the Pillar-7 anti-fabrication structure — every `[E\d+]` marker in the prose must resolve to a
declared `claim_id`, and every declared `claim_id` must be cited (`campaign_plan.py:306,312-333`).

**VT-501 already built the server-side repair I was about to propose.** `_repair_evidence_refs`
(`sales_recovery.py:711`, called at `:853`) heals the `evidence_refs` STRUCTURE from the model's own
prose citations. It is wired and it runs. It **deliberately no-ops when the model cited no markers at
all** — because then there is no grounding to heal from, and a plan with no grounding SHOULD be
rejected.

So the surviving rejections are the case where the model emitted a `proposed` plan with **no evidence
citations anywhere**, i.e. an ungrounded campaign plan, and the gate refused it. The corrective retry
(one per run, naming the failing paths) then recovers it. **Do not "fix" this.** Server-filling
`evidence_refs` would fabricate grounding the model never used, which is a Pillar-7 breach traded for
latency — strictly the wrong direction. The only legitimate lever is reducing the rejection RATE via the
prompt, and prompt nudges have a poor track record on this codebase versus deterministic fixes.

### (c) Where the time ACTUALLY goes — reproduced, and it is not where this row looked

```
T+0s          webhook_received        run fff9fadd   <- owner ask (turn 1)
T+48s   +48s  self_evaluate_gate      run 3da71e0a   <- the async dispatch run
T+52s    +4s  campaign_plan_emitted   run 3da71e0a   <- A PLAN EXISTS AT 52 SECONDS
T+260s +207s  webhook_received        run 69eda6a8   <- owner's turn 2
T+463s +203s  error: schema_rejection run a5edc5fb   <- SR agent's own call was 11-18s of this
T+477s  +13s  self_evaluate_gate      run a5edc5fb
T+480s   +3s  campaigns row PERSISTED                <- the row the gate asserts on
```

**A campaign plan is emitted at T+52s. The `campaigns` row lands at T+480s.** The latency is NOT in
generating a plan — that is fast, and well inside the 96s in-turn budget. It is in everything between
plan emission and persistence.

And the `+203s` gap contains an 11-18s model call, so **~185s is unattributed** — it is spent BEFORE
the SR agent starts (triage / task spawn / dispatch / queue), not inside it.

### What this changes about the scope

- **Item 0 is CLOSED as "not a defect"** (the gate is correct, the repair is wired, the cost is 11-18s).
  It does not make the rest moot; it was never the bulk of the wall clock.
- **Item 1 is now the whole job, and its target is sharper than "instrument the chain".** The gap is
  `webhook_received → SR agent start`, so instrumentation must go at the **dispatch boundaries that
  currently emit nothing at all**, not as a duration on the existing steps. Note the existing steps are
  point-in-time EVENT records (both writers in `pipeline_observability.py` set only `started_at`), so
  adding `ended_at` to them is meaningless — the missing thing is steps at the stage boundaries, plus a
  `duration_ms` the emit seam accepts and persists for callers that already measure one.
- The `campaign_plan_emitted`-at-T+52s vs `campaigns`-row-at-T+480s split is the single most
  interesting measurement in this row and should be the first thing the instrumentation explains.

## Three separate defects, and they must not be conflated

**1. The chain is slow.** ~390s for spawn→SR→draft→arm. Unknown internal distribution — that is
step 1 of the scope, and it is NOT "raise the budget": a 400s in-turn wait would hang every turn.

**2. The promise has no handler.** D1 says *"I'll update you shortly."* In **3 of 6** measured asks
nothing followed, ever. A content-free ack that promises follow-up and then goes silent is worse than
an honest "I couldn't do that" — the owner has no reason to retry and no signal that it failed. This
is the `copy-promises-need-real-handlers` class.

**3. `assert_route` is unsound as written**, and it has been corrupting every gate that used it. It
concludes "did not delegate" from "no `campaigns` row right now". In pass 1 that was **FALSE for 3 of
the 4** scenarios it flagged. **The retracted 24% / 33% / 40% figures are very likely this artifact**,
not a routing defect — which means the numbers quoted in `GO-LIVE-BLOCKERS.md` B1 and the promotion
package are measuring latency and calling it delegation.

## Item 1 BUILT 2026-08-15 — and the substrate answer is not the one the row assumed

The row said to write `ended_at`/`duration_ms` on the step kinds that never had them. That is the
wrong table, for a reason that only shows up when you try it:

**The gap spans RUNS.** The owner's webhook run mints the task; the durable `manager_task_workflow`
that does the work has no `pipeline_runs` row of its own. Every `pipeline_steps` row needs a `run_id`
FK, so a per-run table structurally cannot measure a cross-run handoff — and the cross-run handoff is
exactly the ~185s that was unattributed.

So the boundaries land on **`tm_audit_log`** (`observability/stage_timing.py`): already cross-run,
tenant-scoped, redacted, fail-soft, and keyed by a correlation id — the `manager_task` id, else the
inbound `message_sid`. No migration.

**Four boundaries, two on each side of the handoff:**

| stage | written by | what the interval to the next one means |
|---|---|---|
| `task_minted` | triage (webhook process) | triage → the durable start request |
| `workflow_start_requested` | triage (webhook process) | **the DBOS queue/handoff delay** |
| `workflow_picked_up` | `manager_task_workflow`, before the loop | pickup → the specialist actually starting |
| `specialist_dispatch` | `_dispatch_specialist_step` | everything after is the specialist working |

**T0 is `manager_tasks.created_at`, and the reason is worth keeping.** The obvious design — read this
correlation's previous boundary and subtract — cannot work: `tm_audit_log` grants `app_role` an
INSERT policy and **nothing else** (migration 147; the only SELECT policy requires an operator JWT
claim). A read-back would have returned zero rows in production while passing every test on a
superuser DSN — an instrument reporting `None` for every number, silently. Found by building it that
way first and watching it write nothing. A test now pins the policy set, so if `app_role` ever gains
SELECT this is revisited rather than left as folklore.

`manager_tasks.created_at` is also the only T0 that survives DBOS replay: the workflow re-executes
its code path on recovery, so a Python-local start time would measure the replay, not the wait.

Every mark is fail-soft — an instrument that can throw on the hot path is a latency measurement that
causes outages. `read_stage_timeline(..., dsn=)` is the analysis side and needs the privileged DSN,
which is stated in its docstring rather than left to be discovered.

**Gate (a) is not closed by this.** The instrumentation is landed and unit-proven; the DISTRIBUTION
it exists to produce needs one pack run on the deployed build, which the batch's ×3 will supply.
