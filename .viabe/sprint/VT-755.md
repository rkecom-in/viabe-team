**"Register the Sales Recovery retrieval tools" was sent to a small-business owner on WhatsApp as a

## The mechanism, file:line

`manager/review.py:311-325`. When the SR specialist returns `missing_data`, the Manager composes the
owner question out of the specialist's **`suggested_remediation` field, verbatim**:

```python
remediations = [r for r in (str(item.suggested_remediation or "").strip() for item in plan.missing_data) if r]
if remediations:
    asks = "; ".join(remediations)
    return PlanSpecialistReturn(
        status="needs_owner_input",
        owner_question=("I couldn't build the win-back campaign yet because some information is missing. "
                        f"Could you help with this: {asks}?"),
        ...)
```

`suggested_remediation` is an **engineering** field. Nothing asks whether its contents are something a
business owner could conceivably do. The branch immediately below is already the correct destination for
this case — no remediation ⇒ `blocked` with no proposed outcome ⇒ **ESCALATE**, which its own comment
calls "an honest closure". An engineer-shaped remediation string is precisely what should take that
branch, and instead it takes the owner one.

The design comment above it is right and the implementation misses by one predicate: *"Missing data is
the owner's to supply, so this is exactly what `needs_owner_input` exists for."* True — but the
specialist can classify an **infrastructure** gap as `missing_data`, and then infrastructure remediation
gets read to the owner as if it were their missing data.

## Four defects. Do not conflate them.

**1. An engineering string reached an owner.** O0 / Manager-voice breach: the Manager is ONE entity with
one voice, and "register the Sales Recovery retrieval tools" is not something that entity says to a shop
owner. Decision-independent.

**2. An unanswerable question was asked at all.** Even phrased perfectly, no owner can register a
retrieval tool. When the remediation is not owner-actionable the Manager must ESCALATE (to ops/Fazal),
not ask. The branch exists; the routing predicate is missing. Decision-independent.

**3. Identical re-ask with no no-progress detection.** Answered at 12:26:07, re-asked at 12:26:40 with
byte-identical text. Nothing compares a new question against the just-answered one, so an owner can be
asked the same unanswerable thing forever. This is the loop/stall disease in its purest form — and note
VT-606 already fixed a neighbouring instance (CLARIFY with no question text → REVISE), so this is the
same class recurring at a different predicate. Decision-independent.

**4. THE IMMORTAL PARK — the structural one, and the most dangerous.** That task can never move and
never alerts:

| escape route | why it is closed |
|---|---|
| `_wake_waiting_workflow` (VT-671) | fires only from `mark_approval_resolved`, and `pending_approvals=0`. Also needs `stall_metadata.wait_workflow_id`, and **`stall_metadata` is EMPTY** — the "pre-VT-671 park (no stamp) — the poll ladder covers it" path |
| the retry ladder / orphan reaper | `waiting_owner` is **deliberately EXCLUDED** from the sweep's active set (`task_store.py:280`) so the ladder cannot burn an awaiting-approval task to dead_letter — correct for approvals, and it means a question-parked task is untouchable |
| `pending_questions.correlate_reply` | only flips the row to `answered`. It sends **no** DBOS wake |
| an alert | none. Nothing fires |

So: **`waiting_owner` + no pending approval + no wake stamp = a task that is immortal, silent, and
invisible to every recovery seam we have.** That is a task-class hole, not one bad run.

## Probable root cause, and it connects to VT-752

The remediation text names it: *"Provide a valid evidence source for this run **or register the Sales
Recovery retrieval tools**."* If the SR retrieval tools are not registered/reachable on dev, the
specialist has no evidence to ground a plan in — which is very likely the **same root cause** as the
`proposed.evidence_refs: too_short` schema rejections recorded in VT-752 (100% of schema rejections, one
field). Two symptoms, one cause: **the SR agent cannot get evidence.**

That partially revises VT-752's correction. The rejection IS the honesty gate working — but the model is
not being flaky, it is being asked to ground a plan with no evidence source. **Verify tool registration
on deployed dev before treating either symptom as model behaviour.**

## Scope

1. **Gate `suggested_remediation` before it becomes owner copy.** Owner-actionable ⇒ ask.
   Not owner-actionable ⇒ take the existing escalate branch. Decide by a positive test on the
   remediation's shape, and **do not build a keyword blocklist of engineering phrases** — that is an
   undefined-possibilities list (STANDING, Fazal 2026-07-15). Prefer a structural signal: the
   `missing_data` item's own `category`, plus an LLM judgment on owner-actionability with escalate as
   the fail-closed default.
2. **No-progress detection on re-ask.** A question must not be asked when an identical/equivalent one
   was just answered without the task advancing. On no progress: escalate, don't re-ask.
3. **Close the immortal-park hole.** Every `waiting_owner` task needs exactly one of: a resolvable
   approval, a wake stamp, or a deadline after which it alerts. A parked task with none of the three is
   the defect — detect it and page, reusing VT-746's now-writable alert path.
4. **Verify SR retrieval-tool registration on deployed dev**, and if it is the shared root cause, fix
   that first — it may retire the symptom in VT-752 as well.
5. Re-drive `sr_l2_owner_approval_gates_send` after (1)-(4) and show the question the owner would now
   receive, or the escalation that replaces it.

## Boundaries

- **Do not silence the question by making the Manager guess.** Proceeding without the missing evidence
  would produce an ungrounded campaign — exactly what the `evidence_refs` gate correctly refuses. The
  fix is to escalate, never to fabricate.
- **Do not weaken the approval gate.** Note what did NOT go wrong here: `sends=0`. Nothing was sent
  without approval. This chain is a reliability and owner-quality defect, not a safety one.
- Do not remove `waiting_owner` from the reaper's exclusion — that exclusion protects the 48h approval
  TTL (the VT-668 incident). Add a separate detector; do not widen the ladder.

## Exit gate

(a) No owner-facing question can contain an engineering remediation — proven by driving the specialist's
own `missing_data` path with a non-owner-actionable remediation and asserting an ESCALATION, not an ask.
(b) An answered question followed by no task progress escalates instead of re-asking, proven by
execution. (c) A `waiting_owner` task with no approval and no wake stamp raises an alert — proven by
forcing that state, not by reading the detector. (d) `sends=0` still holds on the re-drive: this row
must not buy reliability with safety.
