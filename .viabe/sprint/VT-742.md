# VT-742 — who do we send as, and what stops one tenant burning it for everyone

## The finding that shapes this row (and corrects Clau)

**VT-286's onboarding half is BUILT, not rostered-and-unbuilt as I twice told Fazal.**
`integrations/whatsapp_account.py` + `api/whatsapp_oauth.py` implement the Embedded-Signup exchange
(code → `access_token` + `waba_id` → provision `phone_number` / `phone_number_id`), and team-web has
`lib/onboard/connect.ts`. `[CODE ✓ 2026-08-10]`

**But the send path never uses it.** `utils/twilio_send.py:710,884,964` all read
`os.environ["TEAM_TWILIO_FROM_NUMBER"]` — a single process-wide constant. So a tenant who completed
Embedded Signup and has their own WABA provisioned **still sends from the shared Viabe number.** We
capture the per-tenant sender and then ignore it. `[CODE ✓ 2026-08-10]`

**That is why this is one row and not two.** Number pinning and owner-owned-WABA need the *same
seam*: a function that answers "which number does THIS tenant send from." Build it once.

## PRE-BUILD INVESTIGATION 2026-08-14 (CC) — three findings, one of which changes what this row IS

Measured on deployed dev before writing any code. **The row is understated: this is not primarily
reputation containment, it is what makes customer conversation two-way at all.**

### 1. It is not hypothetical — 138 live WABA numbers are captured and ignored

```
tenant_whatsapp_accounts rows              : 139
  ... status='live'                        : 138
  ... live AND phone_number NOT NULL       : 138
  ... whose phone_number == the SHARED env sender : 0   (no cross-routing hazard today)
```

The capture path works and populates the column. **138 tenants have a live WABA number and every send
still leaves from the shared env constant.** (Dev is synthetic per CL-422, so these are harness
tenants — the point is the mechanism, not the tenants.)

### 2. THE REFRAME: customer inbound ALREADY requires the tenant's own live WABA, so the shared sender breaks replies

`api/twilio_ingress.py:162` `_lookup_customer_inbound_tenant(to_phone)` resolves a customer's inbound
by:

```sql
SELECT tenant_id FROM tenant_whatsapp_accounts
 WHERE phone_number = %s AND status = 'live' LIMIT 1
```

i.e. **by the number the customer messaged TO.** But we send FROM the shared number, so a customer's
reply arrives with `To` = the shared number, which matches **no** `tenant_whatsapp_accounts` row (0 on
dev, confirmed above) — and the inbound resolves to no tenant.

**So under the shared sender, a customer can be messaged but cannot be heard.** The two halves were
built against different senders. `resolve_sender` is the fix for BOTH, and that raises this row's
value well above "contain reputation": it is a functional gap in the customer conversation loop.

It also names the latent hazard the 0 currently spares us: if the shared number were ever written into
some tenant's `tenant_whatsapp_accounts.phone_number`, `LIMIT 1` would route **every** tenant's customer
replies to that one tenant. Worth an explicit guard when the resolver lands, not just a hope.

### 3. Two different "number" columns, and the resolver must not touch the wrong one

| column | what it actually is | evidence |
|---|---|---|
| `tenants.whatsapp_number` | the **OWNER-inbound identity key**, globally unique (mig 066 partial UNIQUE, VT-267), matched against the inbound's `From` in `_lookup_tenant`; ALSO used as the owner-facing **recipient** by `get_tenant_whatsapp_number` (`twilio_send.py:251`, called from business_plan delivery / daily_initiative / generator) | 235 of 349 dev tenants have it set |
| `tenant_whatsapp_accounts.phone_number` | the tenant's **own WABA sender**, and the customer-inbound routing key | 138 live |

**Migration 050's comment calls `whatsapp_number` "the BUSINESS number (the WABA sender)" — that is
stale.** Nothing in `src/` writes it, it is consumed as an owner identity/recipient, and the actual
sender identity lives in `tenant_whatsapp_accounts`. Also: only **4** of 349 dev tenants have
`owner_phone` set, and in all 4 it DIFFERS from `whatsapp_number`.

**Consequence for the build:** `resolve_sender` reads `tenant_whatsapp_accounts.phone_number` (gated on
`status='live'`, reusing `wa_send_allowed`'s rule rather than re-deriving it) and must **not** read or
write `tenants.whatsapp_number` — touching it would move an owner-inbound routing key and an
owner-notification recipient in one go.

## Scope

### 1. `resolve_sender(tenant_id) -> Sender` — the seam. Everything else hangs off it.
Precedence, evaluated in order:
1. the tenant's **own provisioned WABA**, if present and live (VT-286's output — finally consumed)
2. else the tenant's **pinned shared number**
3. else the default shared number

**Replace all three `os.environ["TEAM_TWILIO_FROM_NUMBER"]` reads with this call.** A hardcoded env
read at the send site is exactly the shape that made the per-tenant WABA dead on arrival. Fail-closed:
unresolvable sender → **do not send**, alert. Never fall through to "some number."

### 2. PIN, never round-robin — standing, decided before the second number exists
When a second sending number is added, **each tenant is assigned one number and stays on it.**
Round-robin spreads one bad tenant's reputation damage across every number we own; pinning contains
it to the tenants sharing that one. This is cheap to decide now and needs a migration to unwind
later, which is the whole reason it is written down before the second number is bought.

**Nursery:** new/unproven tenants pin to a designated nursery number, so a new tenant's bad list
damages a number holding only other new tenants. **Graduation has a real cost** — the customer sees
a different sender — so either graduate EARLY (few prior contacts, cheap) or do not graduate at all
and simply add numbers as the estate grows. **Recommend the second: simpler, and no customer ever
sees the sender change.** Fazal's call if he wants graduation.

### 3. Per-tenant quality accounting
Today the shared number has no per-tenant accountability, so a bad tenant is everyone's problem and
nothing detects it. Track per tenant, rolling: opt-out rate · delivery-failure rate · block-class
failures · zero-read rate · send volume. This is the substrate for (4) and for the VTR console.

### 4. Automatic throttle on the offender, not on everyone
When a tenant crosses a quality threshold, throttle **that tenant** and raise `tenant_alerts` for a
VTR. The failure mode to avoid is degrading everyone equally when one tenant is the cause — which is
what Meta does to us, and what we must not replicate internally.

### 5. Block-signal capture → permanent per-customer hard-stop
When sends to a customer begin failing in the block/spam class, that customer is **permanently
suppressed** (not tiered — VT-741 must never retry them weekly forever) and the event marks the
tenant's quality score. Today nothing captures this and we would keep trying.

### 6. Aggregate per-tenant daily cap
VT-741 bounds per-CUSTOMER frequency. Nothing bounds a tenant's TOTAL daily volume, and aggregate
volume is what moves the Meta quality rating. Config-driven, fail-closed, internal guardrail —
**never an invoice** (CL-2026-08-06-budget-aware-manager: caps are guardrails, not billing).

## Boundaries
- **Zero owner action required for anything in this row.** That is the entire premise of Fazal's
  ruling — if a mitigation needs the owner to do something, it is not a mitigation, it is a blocker.
- Suppression/throttle only. Nothing here authorizes a send.
- No real customer send; allowlist only.
- Do NOT build Embedded-Signup UI or onboarding flow here — that exists. This row CONSUMES it.

## Exit gate
(a) `resolve_sender` is the ONLY source of a sending number — zero `TEAM_TWILIO_FROM_NUMBER` reads
remain at send sites, proven by grep in CI. (b) A tenant with a provisioned WABA demonstrably sends
from their own number and another tenant does not — proven on dev, not asserted. (c) Unresolvable
sender fails closed, proven by forcing it. (d) A block-class failure permanently suppresses that
customer and marks the tenant — proven by forcing the failure code. (e) Quality counters populate on
real dev traffic. (f) Aggregate cap suppresses at the boundary, and the suppression is visible as a
distinct bucket, not as a delivery failure. (g) Pinning is proven with ONE number by asserting the
resolver's precedence — the design must not require buying a second number to be testable.

### The reframe held, and it changed the fix

Scope 1 was written as reputation hygiene. The pre-build investigation found the functional half:
customer inbound resolves the tenant by the number the customer messaged **TO**, so under the shared
sender **a customer can be messaged but cannot be heard**. So a customer-facing send does not
silently downgrade to shared — `require_own_waba=True` REFUSES it. Sending a message the customer
cannot answer is worse than not sending it, and this row is allowed to suppress a send but never to
authorise one (§Boundaries).

### Three decisions taken here rather than escalated

1. **The sender resolves LAST at the template site**, after the VT-460 ungated-customer-send rail and
   the VT-683 whitelist. First build resolved it early to share ONE connection with the recipient
   read; that made a sender fault pre-empt a SAFETY rail, and
   `test_compliance_rail_still_fires_before_dev_guard` caught it — the ungated-customer-send test got
   my error instead of `UngatedCustomerSendError`. A cheaper connection is not worth masking which
   gate refused a send. Cost: two short-lived tenant connections per template send where there was
   one. `get_tenant_whatsapp_number` gained a `conn=` parameter (the VT-460 pattern) for the caller
   that will want to share one.
2. **The pin is a column on `tenants`, not a table.** A number ESTATE registry (nursery designation,
   per-number metadata) lands when the second number is bought; today the estate is one number and a
   table would be a schema shaped around a hypothesis. `TEAM_TWILIO_SHARED_SENDER_NUMBERS` (optional
   CSV) exists so the inbound guard keeps holding the moment a second number arrives, without a code
   change at that moment.
3. **A malformed number is never dispatched, and never silently downgraded either.** A live WABA
   carrying a non-E.164 number logs an error and refuses the customer send; the owner send falls to
   shared. Silence there is how VT-286's output stayed invisible for two months.

### Four pre-existing defects this uncovered

1. **The harness wrote a malformed WABA number for months.** `convo_harness` seeded
   `+1555{tenant_id[:7]}` — uuid HEX, so `+1555470fea5`, which is not E.164. Harmless while the
   column was never read; fatal the moment it became a real sender. Now digits derived from the same
   uuid prefix. **That exact string is also the ONE non-E.164 live number of 134 on dev** — a
   leftover harness row, which my own test then collided with.
2. **Three tests could only pass once against a given database.**
   `test_twilio_send.py::test_send_uses_tenant_whatsapp_number_by_default` inserted a CONSTANT
   `whatsapp_number` against mig 066's partial UNIQUE; `test_whatsapp_account.py`'s `_provision`
   returned a constant number to a tenant it drives to `live`, which mig 207 now makes unique; and
   my own malformed-number test had the same flaw. All three fixed to generate per-run values. The
   first presented as a pooler `EMAXCONNSESSION` error and was actually a `UniqueViolation` — the
   real cause was 40 lines above the noise.
3. **`tenant_whatsapp_accounts.phone_number` had no uniqueness at all** (mig 069), while
   `_lookup_customer_inbound_tenant` reads it with `LIMIT 1`. Nothing violated it (dev: 134 live
   rows, 134 distinct), which is exactly when the invariant is cheap to make structural.
4. **`wa_send_allowed` checks only the STATUS**, so a `live` row with a NULL number passes the send
   gate. The resolver handles it (falls to shared for owner, refuses for customer) and a test pins it.

### Migration 050's comment is stale — confirmed, not just suspected

Nothing in `src/` writes it. The resolver does not read it, and `get_tenant_whatsapp_number`'s
docstring now says so at the call site instead of only in this row.
