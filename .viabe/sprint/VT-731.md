# VT-731 — a missing env var must not silently change vendor

Roster file written after the fact: the commit used id 731 before the allocator had issued it, and
Clau consumed 731 retroactively to re-align the counter. Near-miss, not a collision — but CL-424
exists precisely because two agents reaching for ids informally IS the collision path, and an id
that resolves to no row is how a number becomes untraceable. Recorded rather than tidied away.

## Why
Fazal saw high Sonnet burn on the dev orchestrator key while every tier was believed to be Luna.
The hunt cost a day and turned up two structural problems that were not the cause but were real:

1. **`_TIER_DEFAULTS` fallback on a deployed box.** An unset `TEAM_MODEL_*` silently resolves to a
   built-in Claude default — i.e. a missing variable silently selects a different VENDOR. That is a
   config error wearing the costume of a default. Same family as the docs push that deploys and the
   report bundle that merges: something assumed inert, that isn't.
2. **Vendor-named tier labels.** `select_brain_model` returned `"haiku"` / `"sonnet"` as its
   observability label. The moment the tiers pointed at Luna those names became a LIE in the
   traces — a Luna call labelled `"sonnet"` sends the next investigator hunting a model that was
   never invoked. That is what made this hunt hard.

## What shipped
- `provider.assert_tier_vars_configured()` — logs the RESOLVED model id per tier at boot; on a
  deployed env (`EXPECTED_ENV` set) RAISES `UnknownModelError` NAMING the unset variables. Defaults
  survive for local runs and dev tooling only. Wired into `src/main.py` beside the VT-434 prod-safe
  flag guard.
- Labels renamed `"haiku"`/`"sonnet"` → `"routine"`/`"complex"` in `select_brain_model`, its trace
  line, and the tests. Names that track the TIER survive a provider change; names that track a
  vendor do not.
- Model ids are logged by NAME deliberately: Rule 18 governs credential VALUES; a model id is a
  configuration name, and logging it is what makes the next hunt one grep long.

## Proof
Both arms exercised directly, not just the happy path:
- local + all tiers unset → falls back, logs, no raise
- deployed (`EXPECTED_ENV=dev`) + unset → raises, naming `TEAM_MODEL_CLASSIFIER`, `TEAM_MODEL_COMPLEX`, `TEAM_MODEL_REVIEW`
- deployed + set → resolves all five to `gpt-5.6-luna`

Functional confirmation on deployed dev, by USE not presence (historical `model_used` had cascaded
away with torn-down harness tenants, so live turns were driven with `--keep-tenants`):

```
RESOLVED MODELS on deployed dev: gpt-5.6-luna — 6 steps
```

544 agent+llm tests green; ruff clean.

## What this does NOT fix
**The actual burn.** The tier vars were correct all along and the dispatch brain genuinely honours
Luna. The Sonnet spend comes from direct `Anthropic().messages.create()` call sites that bypass
`resolve_chat_model` entirely. That is **VT-732**, and Clau's independent sweep found 16 literals
across 14 files — ~2.5× the list my own audit produced. Worth stating plainly: one audit's list is
a hypothesis, not an inventory.
