# VT-737 — the flip mechanism had a one-way door

## How it surfaced
Running the VT-725 flip canary on dev (gate (b), unblocked once the recalibrated floor let cards
retrieve at all), the canary's own cleanup crashed:

```
psycopg.errors.RaiseException: specialist_memory_events is append-only (VT-711); UPDATE blocked
CONTEXT: UPDATE ONLY specialist_memory_events SET tenant_id = NULL, assignment_id = NULL
         WHERE $1 = tenant_id AND $2 = assignment_id
```

It also left a live `disabled` assignment row behind on the canary tenant, which would have poisoned
every later baseline on that tenant — the canary is not idempotent when its cleanup fails.

## Root cause — the exemption described behaviour the schema could not produce
Migration 186 deliberately carries an append-only exemption commented *"Preserve event tombstones
when a referenced assignment/card is removed. PostgreSQL's ON DELETE SET NULL is a nested UPDATE"*.
That exemption could never fire, for **two independent reasons**:

1. The FK is **composite** — `FOREIGN KEY (tenant_id, assignment_id) ... ON DELETE SET NULL`. A bare
   `SET NULL` on a composite FK nulls **every** column in it, so the cascade emits
   `SET tenant_id = NULL, assignment_id = NULL`. The exemption requires every column other than
   `assignment_id`/`memory_card_id` to be unchanged, and `tenant_id → NULL` fails that test.
2. `tenant_id` is **NOT NULL**, so even with the trigger removed the cascade would violate the
   column constraint.

So deleting an assignment that had any referencing event raised, always. Same defect on the
`specialist_memory_cards` FK. Fazal ratified the flip as "changeable at runtime"; removing an
override entirely was a one-way door on any tenant that had ever emitted an event.

**Why no test caught it:** nothing ever deleted an assignment that had a referencing event. The DDL
*looked* right and the trigger's comment asserted the intended behaviour, so the gap sat between
"what the comment says" and "what the DDL can do" — where reading either one alone finds nothing.

## Fix — migration 198
PostgreSQL 15+ (dev/prod are on **17.6**) allows a column list on `SET NULL`, so both FKs now null
only their own column and leave `tenant_id` intact — exactly the shape the exemption was written to
allow.

The audit trail is **not** weakened. `assignment_ref` / `memory_card_ref` are separate, permanently
populated columns guarded by `specialist_memory_events_exactly_one_target`; they are the durable
record. Only the live FK pointer is cleared, which is what "tombstone" always meant.

## Proof on dev (not asserted — observed)
Deleting the leaked row after applying 198:

```
events referencing an assignment BEFORE:
  (event 3cbd6a1b…, tenant 42619bde…, assignment_id 4b8dc65b…, assignment_ref 4b8dc65b…, 'write')
assignment deleted OK
same event AFTER (tombstone):
  (event 3cbd6a1b…, tenant 42619bde…, assignment_id NULL,      assignment_ref 4b8dc65b…, 'write')
```

Event survived, `tenant_id` intact, `assignment_id` cleared, `assignment_ref` still holding the
original UUID. Then the VT-725 canary re-ran clean: **`VT-725 CANARY PASS (gates b + d)`** with its
cleanup succeeding.

## Also fixed in the same pass — the canary never booted its own substrate
`vt725_flip_and_narrowing.py` reads through `tenant_connection`, which borrows the module-level
pool, and never called `init_substrate()`. Every read raised, `card_serving` fail-softed to
no-cards, and the canary reported *"tenant A retrieved ZERO cards"* — indistinguishable from a
retrieval failure. It failed LOUD rather than passing, which is the right side to fail on, but it
was measuring the harness rather than the flip. This canary had therefore never actually exercised
gate (b) against real retrieval.

## Tests
`tests/orchestrator/knowledge/test_vt737_assignment_fk_cascade.py` — asserts each cascade names
exactly the column it nulls (a bare `SET NULL` regresses the defect), that neither FK points at the
durable `_ref` columns, and that migration 186 still declares the exemption this fix depends on.
The defect was in DDL, so the test reads DDL.
