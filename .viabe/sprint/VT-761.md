# VT-761 — the same canned sentence twice, and no link either time

## The exchange, identical in pass 1 and pass 2

```
owner:  I use a Google Sheet to track my shop — columns are Customer Name, Phone Number,
        Order Amount, Order Date, and Address.
reply:  No — your Google Sheet isn't connected yet. Want me to set it up?

owner:  Done, I've connected it
reply:  No — your Google Sheet isn't connected yet. Want me to set it up?
```

`i_sheets_mapping_confirm_happy_path`. The scenario's asserts name what should have happened: step 0
expects `'http'` (a connect/mapping LINK), step 1 expects `"don't see the connection"` (an honest
re-check that names what it looked for).

## Two defects, and the second is the serious one

**1. No link on the happy path.** The owner volunteered the exact thing the flow needs — that they use a
Google Sheet, and its column names. That is the moment to hand over the connect link. Instead the Manager
asked a yes/no question with nothing actionable in it. CL-421 is explicit that connectors must be
zero-manual-paste after OAuth; a flow that cannot even produce the link is upstream of that.

**2. THE OWNER ANSWERED AND THE REPLY DID NOT CHANGE.** *"Done, I've connected it"* got the identical
sentence back, byte-for-byte. The owner's turn was not honoured, not acknowledged, and apparently not
consulted. Whether the underlying claim ("isn't connected yet") is TRUE is a separate question — if the
Sheet genuinely is not connected, the honest reply says so *and says what it checked*, which is exactly
what the step-1 assert asks for. Repeating the question is neither.

**Determinism matters here.** Both passes produced byte-identical text, so this is not LLM sampling and
not the persona rewording — it is a deterministic net answering from state it did not re-read. That is
why it clears the VT-611 flake bar at 2/2 rather than needing pass 3.

## The class, which is now three rows wide

| row | the reply | what it failed to consult |
|---|---|---|
| **VT-756** | "You currently have 0 customers in your ledger" | whether a data source is connected at all |
| **VT-761** (this) | "isn't connected yet. Want me to set it up?" ×2 | the owner's own answer, and/or the live connection state |
| VT-755 | an identical question re-asked after it was answered | that the previous one was already answered |

**One shape: a deterministic reply asserting state without re-reading the thing it asserts about.** Worth
fixing as a class rather than three times — and worth noting that all three are on the honesty floor, not
the money path.

## Scope

1. **Produce the link when the owner names their source.** "I use a Google Sheet" + column names is the
   strongest connect signal available; that turn should hand over the mapping link, not a yes/no question.
2. **Re-check on the owner's confirmation.** *"Done, I've connected it"* must trigger a live read of the
   connection state, and the reply must state what was checked — the step-1 assert (`"don't see the
   connection"`) is asking for exactly that honesty, not for a different mood.
3. **Never emit the same canned sentence twice in a row on the same topic.** This is the same no-progress
   detection VT-755 scope 2 needs; consider whether one guard serves both rather than two.
4. **Check whether "isn't connected yet" was even TRUE** at the second turn. If the Sheet was connected and
   the reply denied it, this is a stale-read defect and more serious than a copy problem — that
   determination changes the priority and must be made before the fix.

## Boundaries

- **Do not fix this by softening the assert.** The scenario is right: a happy-path connect turn should
  produce a link, and a confirmation should produce a re-check.
- Do not paper over it with an LLM rephrase so the two replies differ cosmetically. The defect is that the
  owner's turn changed nothing, not that the wording repeated.
- CL-421 holds: whatever link is produced must be zero-manual-paste after OAuth.

## Exit gate

(a) An owner naming their Sheet receives a connect link, on deployed dev. (b) *"Done, I've connected it"*
produces a reply that differs from the previous one and names what was checked. (c) The truth of "isn't
connected yet" at the second turn is established and recorded (scope 4) — if it was false, this row's
priority is raised and the stale read is named. (d) `i_sheets_mapping_confirm_happy_path` passes on the
same transcript shape, and a genuinely-unconnected tenant still gets an honest not-connected answer.
