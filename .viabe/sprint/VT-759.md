# VT-759 — the assert is in English and the Manager answered in Hinglish

## Three failures, all inspected, all the same shape

**1. `readiness_ask_then_defer_and_resume`** — `assert_contains: ['hold off']`

```
owner:  nahi abhi nahi, baad mein karenge          ("no, not now, we'll do it later")
reply:  Theek hai, abhi hold kar dete hain. Jab aap ready hon, yahin se continue kar lenge.
        ("Fine, let's hold it for now. When you're ready we'll continue from here.")
```

The behaviour the assert exists to guarantee — acknowledge the defer, hold, offer to resume — is **exactly
what happened**, and the reply even uses the word *hold*. It fails because the literal is `hold off`.

**2. `profile_preview_then_confirm`** — `assert_contains: ['one at a time']`

```
owner:  haan bilkul, yehi sahi hai
reply:  Badiya 👍 Aapka business kya sell karta hai ya kaunsi service deta hai?
```

"One at a time" is a requirement about **pacing** — ask one thing per turn. The reply asks exactly one
thing. The behaviour is satisfied; the assert demands the Manager narrate the pacing rule out loud.

**3. `sr_stop_then_resume_no_false_autosend_claim` step 2** — `assert_contains: ['sure']`

The reply produced a real draft (5 customers, lapsed-45d-plus, 14–21 Aug, ₹300–₹700 expected), asked for
approval, and made **no false send claim** — the honesty property that scenario exists to protect. It failed
on the absence of the word *sure*.

## Why this is worse than three cosmetic failures

**An English literal asserted against a Hinglish reply can only pass by accident.** These scenarios drive
code-mixed conversations on purpose (`m_conversation_hinglish_*`, and the readiness/profile flows reply in
the owner's register). Whether the assert passes then depends on **which language the Manager happened to
answer in**, not on what it did. So the assert is:

- **flaky by construction** — it passes when the reply drifts English, fails when it drifts Hindi, and the
  behaviour is correct in both cases;
- **measuring the wrong thing** — the same error VT-753 found in `assert_route` (a routing verdict from a
  latency fact) and VT-758 found in `expect_sent_count` (a safety verdict from an unqueried default). This
  is the third instance of one family: **an assertion whose observable does not match the claim it makes.**

And it **inflates the gate's own number**: 3 of gate (d) pass 1's 17 non-clean scenarios are this. 86.9%
clean is therefore a FLOOR — the ceiling with these corrected is 88.5%. Whoever quotes the gate needs that.

## Scope

1. **Assert the BEHAVIOUR, not the vocabulary.** Each of the three has a real requirement underneath:
   defer-acknowledged-and-resumable; one-question-per-turn; approval-requested-without-a-send-claim. Two are
   already expressible with existing primitives (`assert_not_contains` on send-claim phrases is what the
   third scenario ALREADY uses successfully, alongside the failing `assert_contains`).
2. **Where a phrase genuinely is the requirement, make it language-aware.** A required reassurance token in a
   Hinglish conversation must accept the Hinglish form, or the scenario must pin the reply language first.
   **Per the standing no-lists rule this is NOT an invitation to add a synonym list** — if the requirement
   cannot be expressed without enumerating phrasings, it is a behaviour and belongs in (1).
3. **Sweep every `assert_contains` in the pack for the same shape** — an English literal in a scenario that
   drives or permits a non-English reply. This is a class; three is what gate (d) reached, not what exists.
4. **Re-state gate (d)'s clean rate** once corrected, and note in the gate report that the pre-correction
   number was a floor.

## Boundaries

- **Do NOT loosen an assert to make a run pass.** The test is whether the BEHAVIOUR held; two of these three
  I verified held, and the third (`profile_preview`) held on the pacing requirement. If a behaviour did not
  hold, the assert stays failing.
- Do not "unify" the reply language to suit the asserts. Code-mixed replies in the owner's register are the
  product working (CL-443 WhatsApp-first conversational primary); the scenario must adapt to the product,
  not the reverse.
- Do not fold this into a judge rescore. The judge already re-scores semantics; this row is about the
  DETERMINISTIC asserts making claims their observable cannot support.

## Exit gate

(a) Each of the three scenarios asserts its underlying behaviour and passes on the SAME transcript that
fails today — proving the behaviour was always correct and the assert was wrong. (b) A deliberately WRONG
reply on each still fails, so the fix did not simply delete the check. (c) The pack-wide sweep is published:
every `assert_contains` English literal in a scenario that permits a non-English reply, with each either
corrected or shown safe. (d) Gate (d)'s clean rate is re-stated with the correction and the original number
labelled a floor.
