# VT-764 — a runaway guard that fires on every run and stops nothing

`orchestrator_agent_driver.ORCHESTRATOR_TOKEN_HARD_LIMIT = 10_000`, counted as `tokens_input + tokens_output`
per invocation. The brain's system prompt is ~18k tokens, so `cumulative_tokens > 10_000` is TRUE after the
first call of every run. The check runs inside `check_mid_invocation`, called from the callback; the raise
propagates into langchain's callback machinery, which **catches handler exceptions and logs
`Error in <handler> callback:`** unless `raise_error=True`. Net: an ERROR log line per LLM/tool boundary per
run, and no abort. The manager domain passed 86.8% in the same window, so the runs plainly complete.

Two defects, pick both: (1) the limit was sized before the prompt grew (VT-617 raised the tool-call limit
5→10 for the same "reframed role" reason and left tokens at 10k); (2) the guard's failure mode is silent —
a guard that cannot abort should not exist. Fix: size the token axis to what the role actually spends
(input is prompt-dominated and not a runaway signal; guard OUTPUT + tool calls + wall clock), and make the
breach path either abort or be a metric, not a swallowed exception. Also decide whether the noise is
hiding real errors in the log stream (it is the loudest line in the window).

|---|---|---|---|---|---|
| `complex` (the brain) | 432 | 42 | 359 | **728** | **68,184** |
| `sr_draft_turn` | 338 | 1,140 | 2,995 | 4,946 | 24,575 |
| `gap_compose` | 195 | 1,477 | 1,803 | 2,238 | 3,528 |
| `self_evaluate_gate` | 190 | 547 | 1,137 | 1,732 | 6,138 |
| `turn_brain_tools` | 202 | 351 | 702 | 904 | 9,248 |
| `triage` | 980 | 72 | 214 | 490 | 4,667 |

Per-call input for the brain: **p50 16,780 / max 17,656** — so the retired `input + output > 10_000`
check was TRUE on the first call of every run, exactly as the rostering note said, now with a number
instead of an estimate. The in+out max of **68,184** is the line that settles it: the limit sat 6.8x
UNDER real observed spend, so it was never a runaway threshold at all.

**8_000 output tokens** sits ~11x above the brain's observed max and ~1.6x above the largest
per-invocation output measured anywhere in the system, so a legitimate multi-tool turn cannot trip it
while a genuine runaway generation will. Input tokens are PROMPT SIZE — a deploy-time property with
its own gate (`gate-sr-agent-prompt-token-cap`) — and do not belong on a runaway axis.

### Why the two fixes had to land together

Making the raise propagate while the limit stayed at 10k combined would have aborted **every brain
run**. That is worth stating because the two looked like independent items on the roster and are not.

### The failure mode, closed

`raise_error = True` on `OrchestratorReasoningCallback`. langchain's callback manager catches handler
exceptions and logs `Error in <handler> callback:` unless the handler opts in — which is why
`dispatch_brain`'s `except HardLimitExceeded` branch and its `aborted_hard_limit` envelope had never
executed. Because that flag makes ANY handler exception propagate, each handler's observability work
is now individually wrapped (`_account_and_record`, the node stash, both `emit_tm_audit` calls), so a
`write_step` / metering / audit failure still cannot cost a turn (CL-122) and only a limit breach
escapes. Same shape `llm/provider.py` already used.

One structural detail worth keeping: in `on_llm_end` the limit check sits AFTER the guarded
accounting block and OUTSIDE it, so a breach still aborts even when the accounting above it failed —
pinned by `test_the_limit_check_still_runs_after_an_accounting_failure`. A guard reachable only on the
happy path is the same class of defect as this row.

### Not done here

Whether the ERROR noise was **hiding** real errors in the log stream is not answered — the line is
gone from future runs, but nothing re-read the historical window for what it masked. Left open in
this row rather than quietly dropped.

## CORRECTION 2026-08-17, and a second defect found making it

I wrote — in the row, the commit message and my signal to Clau — that `dispatch_brain`'s
`except HardLimitExceeded` branch and its `aborted_hard_limit` envelope **"had never once executed."**
**That is wrong, and measured evidence says so.** From dev:

```
pipeline_runs WHERE status = 'aborted_hard_limit', by day
  2026-08-17  n=4      2026-06-30  n=23     2026-05-26  n=1
  2026-07-03  n=1      2026-06-28  n=16     2026-05-24  n=1  …  (74 total)
```

So the abort path HAS fired, ~74 times. What was actually dead is narrower and still true: a
**callback-originated** breach could not abort, because langchain's manager catches handler exceptions
without `raise_error`. That is the defect this row fixes. The overclaim was mine and it mattered — it
implied a whole branch was untested when the branch was live.

**How I found it:** the 4 runs dated today are at **13:10–13:14Z**, which is BEFORE the pack started
(14:05Z) and before the 13:50Z deploy — i.e. they came from my own dev realdb test runs, not from the
pack and not from any build carrying this change. I nearly filed them as "a new failure class from the
pack".

### The second defect (rostered, not fixed here)

`step_kind = 'aborted_hard_limit'` has **0 rows, ever.** So while 74 runs were marked aborted, the
envelope that records WHICH AXIS fired, observed-vs-limit, and the tenant/run — the only thing that
makes an abort diagnosable — has never been written once. `_write_aborted_hard_limit`'s `write_step` is
wrapped in a swallow (`"aborted_hard_limit write_step swallowed"`), so either it always fails or it is
never reached on the path that sets the status. **Same shape as this row's own defect one layer along:
the observability of the guard is silent in exactly the way the guard was.** Not fixed here because I
have not yet established WHICH raiser sets the status without the step — guessing the path is how the
first overclaim happened.
