# VT-778 — DataForSEO as a name→GSTIN discovery leg

Fazal 2026-08-21: *"its our DataForSEO Api, it can give both Google Organic Search and AI Mode
response. Can we try to check if that can work for us to get the more legit GSTIN."*

Evaluated with the real credential (`DATAFORSEO_API_BASE64`) via
`apps/team-orchestrator/canaries/dataforseo_gstin_eval.py`. Scored against KNOWN TRUTH, because the
deciding question is PRECISION, not recall — a plausible GSTIN for the WRONG company is the VT-406
Sundaram failure, and Sandbox cannot catch it (it confirms the number is real and ACTIVE because it
belongs to *somebody*).

## Results

**Balaji Wafers** (ground truth: PAN `AAACB8755A`, several state GSTINs)

| source | verdict | correct | same-PAN siblings | NOISE (other companies) | paired w/ name |
|---|---|---|---|---|---|
| organic `"Balaji Wafers" GST number` | HIT | 2 | 3 | **4** | 6 |
| organic `Balaji Wafers GSTIN` | HIT | 2 | 2 | **3** | 4 |
| **AI Mode** | **HIT** | 1 | 3 | **0** | 4 |

**RKeCom Services** (ground truth: `27AAKCR3738B1ZE`)

| source | verdict | correct | NOISE |
|---|---|---|---|
| organic `"RKeCom Services" GST number` | NOTHING | 0 | 0 |
| organic `RKeCom Services GSTIN` | **NOISE-ONLY** | 0 | **10** |
| AI Mode | NOTHING | 0 | 0 |

## What this says

**1. AI Mode is the best candidate source we have tested — by precision.** Four GSTINs returned for
Balaji, ALL of them Balaji's (one exact + three same-PAN state registrations), **zero belonging to
other companies**. Organic returned 3–4 strangers' GSTINs alongside the right ones every time.

**2. AI Mode returned NOTHING for RKeCom rather than inventing something.** This is the behaviour
that matters most and it is the direct contrast with VT-777: ungrounded Gemini asked the same
question fabricated `07AAGCR4831R1ZB`. AI Mode is grounded in real results, so it declines. An
honest miss is worth more than a confident wrong answer, because a wrong answer that is *valid*
survives the Sandbox gate.

**3. Unquoted organic is actively dangerous.** `RKeCom Services GSTIN` returned **10 GSTINs, none of
them RKeCom's, none paired with the name** — exactly the noise class VT-448 was opened for. It must
never feed candidates without the `_significant_tokens` relevance filter.

**4. Neither source finds RKeCom.** As predicted before running: Google has not indexed the
knowyourgst page (`site:knowyourgst.com "RKeCom Services"` → 0 results). Every Google-derived source
inherits that blind spot. **The Firecrawl/knowyourgst FORM scrape stays primary** — it is the only
thing that finds Fazal's own company.

## Cost

Balance $0.918 → $0.890 across ~7 calls = **~$0.004 per lookup** (empirical, not quoted — the
`price` structure did not expose per-endpoint rates). At 1000 signups/month that is ~$4/month.
Cheap enough not to be a factor.

## Recommendation

Add **AI Mode only** as the discovery cascade's second leg, ahead of the Gemini leg:

```
Firecrawl/knowyourgst form scrape   (primary — finds what Google cannot index)
  └─ empty → DataForSEO AI Mode     (grounded, zero-noise, honest miss)
      └─ empty → Gemini + grounding (VT-777 guard: verbatim-in-grounded-text only)
          └─ empty → owner types the GSTIN → Sandbox verify
```

Do **not** adopt organic search as a candidate source. If it is ever used, it needs the VT-448
relevance filter and GSTIN-must-be-paired-with-a-matching-name, which is most of the work with none
of AI Mode's precision.

Apply the VT-777 discipline to AI Mode too: it is a synthesised answer, so accept a GSTIN only when
it is paired with a name matching the queried business. It is a HINT. Sandbox stays the sole gate.

## BUILT (Fazal: "Go ahead with your recommendation")

New `integrations/methods/dataforseo.py`; wired into BOTH discovery paths.

### The correction that only appeared during the build

**The evaluation's headline conclusion was wrong, and I caught it while canarying.** The eval said
AI Mode "declines rather than invents" because one run returned nothing for RKeCom. A second run
returned **`27AAECR0564M1Z3`** — a well-formed Maharashtra GSTIN that is NOT RKeCom's — inside the
sentence *"If you need to verify or pull their exact 15-digit GSTIN, you can..."*. An illustrative
number in synthesised prose, indistinguishable from a real answer once the surrounding words are
stripped away.

**One sample said safe. The second said otherwise.** The recommendation was built on a single
observation of a non-deterministic system.

### The fix — same discipline as VT-777

Extraction reads AI Mode's `references` array ONLY (the sources it actually cited), never its prose:

| business | prose GSTINs | reference GSTINs |
|---|---|---|
| Balaji Wafers | 24AAACB8755A2Z0, 24AAACB8755A4ZY | **same two** — the prose was grounded |
| RKeCom Services | `[]` one run, a FABRICATED GSTIN the next | **`[]` both runs** |

Accept only what a real source said, never what the model synthesised. Costs nothing when the model
is right; it is the entire defence when it is wrong. A cited GSTIN must ALSO sit in text echoing a
distinctive token of the queried name — AI Mode cites competitors, suppliers and generic
"GST registration in Mumbai" pages.

### The cascade, both paths

```
knowyourgst form scrape  →  DataForSEO AI Mode  →  Gemini+grounding  →  owner types it
```

Each rung paid only if the one above found no GSTIN. Applied in `entity_match.fetch_candidates`
(sync endpoint + WhatsApp journey) AND the VT-507 async API (the web signup).

`both_complete_zero` was hardcoded to two sources; now generalised over `_SOURCES`. Field keeps its
name — team-web reads only that flag and never the source list, so the third rung is invisible to
the UI.
