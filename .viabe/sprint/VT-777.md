# VT-777 — the "LLM + web search" secondary is running LLM-only

## The finding

Fazal asked for a Gemini **LLM + WebSearch** secondary for name→GSTIN (VT-776). The model runs.
The search does not.

Ledger evidence from deployed dev (`llm_call_events`), after 5 real discovery runs:

```
gemini-3.5-flash  llm_discovery  search_count=0   search_cost=$0.000000
gemini-3.5-flash  llm_discovery  search_count=0   search_cost=$0.000000
gemini-3.5-flash  llm_discovery  search_count=0   search_cost=$0.000000
gemini-3.5-flash  llm_discovery  search_count=0   search_cost=$0.000000
gemini-3.5-flash  llm_discovery  search_count=0   search_cost=$0.000000

SELECT COUNT(*), SUM(search_count) FROM llm_call_events WHERE provider='google'
  -> (5, 0)
```

**Zero grounded searches, ever.** For google, `search_count` is 1 when
`response_metadata['grounding_metadata']` carries any `web_search_queries`
(`usage_callback._extract_search_cost`). Zero means the model did not search.

## What is NOT the cause (checked)

- **Master flag is ON.** `TEAM_ENABLE_WEB_SEARCH` on dev == `yes` (verified via
  `env_presence.py equal` against literals — MATCH on `yes`, MISMATCH on `true`/`1`/`on`).
  `_web_search_master_on()` accepts `{"1","true","yes"}`, so it is on.
- **The call site requests it.** `_default_llm_search` passes `enable_web_search=True`.
- **The binding form is the documented one.** `_apply_search_tools` sends google down
  `bind_tools([{"google_search": {}}])`, which is the SDK-verified form for the provider.
- **Not a metering gap.** The google branch of the extractor exists and is specifically
  written for grounding metadata; it is not an unmapped provider.

## Leading hypothesis — NOT yet proven, do not treat as fact

The system prompt is *"You MUST respond with ONLY valid JSON — no prose, no markdown"* and the
user prompt repeats *"Your ENTIRE response must be parseable by json.loads()"*. Gemini grounding is
model-DISCRETIONARY; a hard JSON-only instruction plausibly suppresses the tool call. There is a
second candidate: Google has historically disallowed grounding together with structured-output
constraints, so the two may be mutually exclusive on this path.

**Both are untested.** Testing needs a `GEMINI_API_KEY`, and there is no `gemini.env` in
`.viabe/secrets/` (only `google-oauth.env`, which is OAuth client creds — a different thing).
The key is sealed on Railway, so `railway run` cannot see it either.

## Why this matters — the risk is NOT just wasted spend

This is the **Sundaram bug class** (the reason VT-406 exists). An ungrounded model asked for the
GSTIN of an obscure Indian business answers from parametric memory. The failure mode that matters is
not an invalid GSTIN — Sandbox rejects those. It is a **plausible, VALID GSTIN belonging to a
DIFFERENT company**: the owner picks it, Sandbox verifies it as real and ACTIVE, and the tenant is
anchored to the wrong legal entity. Discovery is hints-only, but the verify gate confirms the
GSTIN exists — it cannot know the owner picked someone else's.

Current mitigations are thin for this specific case: the leg drops name-only entries and uses the
LLM-reported registered name, and `_significant_tokens` relevance filtering applies to the WEB leg,
not the LLM one.

## Next steps

1. Get a `GEMINI_API_KEY` into `.viabe/secrets/gemini.env` (Fazal) so the hypotheses can be tested
   locally instead of guessed at.
2. Test: relax the JSON-only instruction and see whether `search_count` becomes non-zero; and test
   grounding with/without structured-output constraints.
3. If grounding cannot be made to co-exist with strict JSON, split the leg in two calls —
   grounded search first, then a cheap extraction pass over the grounded text.
4. Until grounding demonstrably fires, treat the Gemini leg as **low-trust**: consider gating it
   behind an explicit "found on the web, unverified" presentation, or holding it off until fixed.

# RESOLUTION (2026-08-21, commit 8059164a)

## Root cause — PROVEN, not hypothesised

Isolated locally with the real `GEMINI_API_KEY` by varying ONE thing at a time. Same model, same
key, same master flag:

| probe | prompt | grounding | result |
|---|---|---|---|
| A | strict-JSON (production) | ON | **0 search queries** — `{"companies": []}` |
| B | strict-JSON | OFF (control) | **FABRICATED `07AAGCR4831R1ZB`** for "RKECOM SERVICES PRIVATE LIMITED" |
| C | prose | ON | **1 search query** `"RKeCom Services"` — grounding fires |
| D | no system prompt | ON | 0 queries |

The JSON-only instruction suppresses Gemini's discretionary grounding. Confirmed.

**Probe B is the finding that matters.** The real registration is `27AAKCR3738B1ZE` (27 =
Maharashtra). The model invented `07AAGCR4831R1ZB` (07 = Delhi) — well-formed, plausible, and for
the wrong entity. This is the VT-406 Sundaram bug arriving through a new door, and the Sandbox gate
cannot catch it: it confirms a GSTIN is real and ACTIVE because it belongs to *somebody*. It cannot
know the owner picked the wrong somebody.

## The fix — structural, not a better prompt

Two calls plus a hard guard:
1. PROSE search call (grounding fires);
2. **no search query issued -> ZERO candidates.** Fail closed: an ungrounded answer is a memory
   answer, and finding nothing beats anchoring a tenant to a stranger;
3. extraction call over call 1's text only, no search of its own;
4. every GSTIN must appear **verbatim** in the grounded text or it is dropped.

Fabrication is now impossible rather than discouraged.

## Second defect found while fixing

Extraction at `max_tokens=512` truncated the JSON mid-object, so every candidate was lost to the
parse and the leg read as "found nothing". Raised to 2048 — it reads a whole search result.
