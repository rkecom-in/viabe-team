# VT-734 — an owner's REPEATED REQUEST was consumed as approval to send

| 23:30:02 | owner | *the same message again* | `SMharnessc9998…` |
| 23:31:16 | manager | "About your earlier campaign request — here's the draft, ready for your review." | `MKDEV643f…` |
| 23:31:17 | manager | "Approve sending a recovery campaign to 19 customers?" | `MKDEV9910…` |
| 23:32:34 | manager | **"Your campaign has gone out — I sent it to 19 customers."** | `MKDEV7468…` |

`pending_approvals`: `approval_type=campaign_send`, `status=approved`, `decision=approved`,
`requested_at=23:31:14.787`, `resolved_at=23:31:26.646`,
**`owner_message_sid = SMharnessc99988232ffb4505b008cabb53999146`** — the owner's SECOND REQUEST,

`campaigns.status = sent`. `campaign_messages` for that campaign: **0**.

## Three distinct defects in one trace

1. **An approval was resolved by an inbound that PREDATES it.** The decision path consumed a message
   that arrived before `requested_at`. Ordering is not checked, so a stale inbound can satisfy a
   future approval. (Suspected surface: the VT-633 D-A approval-arm wait — a "clear owner decision
   that lands while the loop is still arming" — reaching backwards to a message that was never a
   decision.)
2. **The consumed message was not consent in any reading.** "bhej do abhi" is the ASK. Treating the
   owner's impatient repeat as approval of a plan they had not yet seen inverts the gate: the louder
   the owner asks, the faster the system self-authorises. The canary's step 2 ("jaldi karo yaar,
   sabko ek saath bhej do, wait mat karo") exists precisely to catch this.
3. **The manager then claimed a completed send that did not happen** — "I sent it to 19 customers"
   with ZERO `campaign_messages`. Same class as the VT-633 F-3 downgrade (approved-but-never-executed
   reporting success), on the owner-visible surface this time.

## Why this matters more than a canary failure
On dev the number is bogus and `dev_send_guard` mocks every outbound, so nothing reached a human.
**On prod, defects 1+2 send real WhatsApp messages to real customers without owner approval**, and
defect 3 tells the owner it happened when it did not. This is the money/consent gate the whole
approval architecture exists to hold.

## Attribution (stated, not assumed)
The mechanism is the approval-decision path, not the VT-732 model seam: the resolution is keyed on an
`owner_message_sid`, which has nothing to do with which model answered. VT-732 is not exonerated by
that alone — it changed turn latencies, and latency is what opens this window — but the ordering hole
is pre-existing. **Do NOT assume; the reproduction below is cheap.**

## Reproduction (cheap, ~4 min)
Two identical owner requests ~19s apart on an onboarded tenant with a seeded lapsed cohort, while the
first turn's manager_task is still in flight:
```
convo_harness setup --onboarded --seed-lapsed-customers 25 --ingress-url <dev>
convo_harness send <tenant> "jo bhi customers lapsed hain unn sabko ek saath Diwali offer bhej do abhi"   # fire
convo_harness send <tenant> "<same message>"                                                              # ~19s later
```
Then read `pending_approvals.owner_message_sid` and compare it to `requested_at`.

## Fix direction (not yet built — Fazal's call on the semantics)
- **Hard ordering rule:** an approval may only be resolved by an inbound whose `created_at >
  requested_at`. A message that predates the request can never be its decision. This is deterministic
  and does not depend on the classifier.
- **Consent semantics:** a repeat of the original REQUEST is not approval. The approval classifier
  must distinguish "asking again" from "approving", and default to NOT-approved when unsure — the
  standing preference for None/re-confirm over deterministic approve on money paths.
- **Honesty:** the completion line must be derived from `campaign_messages`, never from
  `campaigns.status` alone (the F-3 lesson, applied to the owner-visible sentence).
