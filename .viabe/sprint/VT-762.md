# VT-762 — the VT-732 trap, on the other provider

## How it was found

The M2 pack ×3 (post-batch build) came back 119/119/115 clean against gate (d)'s 113/112/113 — a
net gain of ~6 scenarios, all six targeted rows fixed to CCC. But **six scenarios that were CCC in
gate (d) became flips**, every one of them the same signature:

```
assert_route: expected delegation to Sales-Recovery this turn, observed route='none'
assert_side_effects: expected campaign row present=True, found=False
```

All SR-lane. All win-back asks. Under the ×3 rule a flip is variance — but six new flips in one lane in
one batch is a mechanism until proven otherwise, so I reproduced the classifier locally against the
exact eight delegation-expecting messages, ×3 each:

```
triage_turn: Anthropic call failed (fail-soft -> None)
ValueError: empty response from triage (complex) call: model='claude-sonnet-5'
            stop_reason='max_tokens' max_tokens=200
```

**8 of 24 calls returned None.** Raw response on a failing call:

```
stop=max_tokens  out_tokens=200  blocks=['thinking']   text: <empty>
```

## The mechanism

`llm/provider.py` already has a reasoning floor (VT-732): on the Responses-API providers the cap
covers reasoning tokens, so a small cap returns no text, and every small cap is floored to 1024. Its
own comment says *"Anthropic's `max_tokens` does not behave this way"* — and that was true of the
models the caps were tuned on. **The Claude 5 family thinks by default** (adaptive thinking, no
`thinking` param passed anywhere in `llm/`), and its thinking blocks count against `max_tokens`.
Triage asks for 200. Sonnet-5 spends 200 thinking, emits no text, `structured_text_call` raises,
`triage_turn` fails soft to `None`, and the seam falls back to legacy dispatch — which does not
reliably delegate. The system looks fine and quietly runs without its classifier: the exact class
VT-732 named.

**Why it surfaced now.** Two things in my own batch made the truncation more likely, on a trap that
was already there: VT-757 appended the capability surface to the system prompt (6.8k → 8.6k chars,
so the model thinks longer) and added two fields to the JSON (the non-thinking reply grew from ~35 to
~85 tokens). Two of the ten stable-failing scenarios in gate (d) — the two with the LONGEST asks —
were very likely this trap before my batch touched anything; they are now 3/3 `campaign_recovery`.

## The fix

`_effective_max_tokens` now floors the cap for the Anthropic models that think unprompted
(`claude-sonnet-5`, and the `opus-5` / `fable-5` names so the floor follows the family the day either
is added). Non-thinking Anthropic models keep the caller's hand-tuned cap — some sites use it as a
length limiter, and that contract is pinned in the existing test. The floor itself goes 1024 → 2048:
at 1024 sonnet-5 still cut a dual-intent triage JSON mid-field 1 in 24. **A cap is not a spend** —
the model emits what it emits; a floor that is too low bills the thinking and discards the answer.

Probe after the fix: **0/24 None** on the eight messages, and the dual-intent ask 6/6.
