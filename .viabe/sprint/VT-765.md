# VT-765 — we can message a customer, and we cannot hear them answer

## The mechanism, in two lines of shipped code

`api/twilio_ingress.py` resolves an inbound in this order:

```python
tenant_id = _lookup_tenant(from_phone)                      # OWNER: matches tenants.whatsapp_number
if tenant_id is None:
    customer_tenant = _lookup_customer_inbound_tenant(to_phone)   # CUSTOMER: matches
                                                                  # tenant_whatsapp_accounts.phone_number
                                                                  # WHERE status='live'
```

Customer inbound is resolved **by the number the customer messaged TO**. Every send leaves from the
shared Viabe number (Fazal 2026-08-17, and it was already true before VT-742). The shared number is in
no tenant's `tenant_whatsapp_accounts` row — measured on dev: **0 of 134 live rows carry it** — so a
customer's reply matches nothing and resolves to **no tenant**. It falls through to the unknown-sender
path.

**So the outbound half and the inbound half were built against different senders.** This is not a
VT-742 regression: it is what shipped, and VT-742 only made it visible.

## Why the obvious fix is forbidden

Requiring the tenant's own live WABA so that `To` matches their row would make a customer send depend
on **owner action** — Embedded Signup, business verification, display-name approval. Fazal, twice:

> *"Having owner-owned WABA is a dependency that we won't be able to manage to meet as it has the
> owner to take certain actions… Unless these entire thing can be automated without the owners
> involvement, these will just act as blockers."* (2026-08-10)

> *"And for now we will be sending all communications from the Viabe number."* (2026-08-17)

And VT-742's own Boundaries: **zero owner action required**. I built that forbidden version first;
this row exists because the ruling is right and the gap still has to be closed some other way.

## The hard part — one shared number is AMBIGUOUS by construction

Resolving by the customer's `From` instead of `To` is the obvious alternative and it does not simply
work: **the same customer phone can belong to more than one tenant.** Two shops can have the same
person as a customer. Under one shared number, an inbound from that person carries nothing that names
which shop they are answering.

Candidate resolutions, none free, all needing a decision:
1. **Most-recent outbound wins** — resolve to the tenant that last messaged this phone inside an open
   session window. Deterministic, no owner action, and it is what the conversation actually means most
   of the time. Fails when two tenants messaged the same customer in the same window; needs an
   explicit tie-break rather than a silent pick.
2. **A per-tenant reply token in the outbound copy** — customer-hostile for a WhatsApp reply
   (nobody quotes a code back) and it collides with CL-421's zero-manual-paste rule in spirit.
3. **A number per tenant that WE own and provision** — no owner action at all, so it satisfies the
   ruling, but it is an estate cost and it is exactly what VT-742 §2's pinning was written to defer.

**Fazal decision required on 1 vs 3** (2 is a non-starter in my read). Recommend **1 now** — it is
free, deterministic, and needs no new numbers — with **3** as the growth path once the estate exists,
because option 1's ambiguity gets worse the more tenants share the one number.

## Not to be confused with

- **The consent/opt-out rails.** An unresolved customer inbound means a STOP from that customer may
  not reach the tenant it belongs to. That is the part that makes this Critical rather than merely
  broken: `handle_customer_inbound` records opt-out state per tenant, and it never runs.
- **`wa_send_allowed`** (see below) — a separate pre-existing dependency, also owner-action-gated.

## The adjacent finding this exposed, for Fazal not for me

`customer_send_choke.assert_customer_send_allowed` gates **every** customer send on
`wa_send_allowed(tenant_id)`, which is TRUE only when `tenant_whatsapp_accounts.status = 'live'` —
i.e. after Embedded Signup + Meta business verification + display-name approval. **That is an
owner-action dependency in front of every customer send, and it predates VT-742.** Under "all
communications send from the Viabe number", a send that uses none of the tenant's WABA is still
blocked until the owner completes one.

I have NOT touched it: it is a correctness gate in the family that never bends to make something pass,
and Meta's own rule (a tenant cannot send under their own WABA pre-verification) is the reason it was
written. But if the product intent is that Viabe's number carries the traffic, then the gate is
guarding a premise that no longer holds for that path, and only Fazal can say so. **Raised, not
changed.**

## Exit gate

(a) A customer's reply to the shared number resolves to the correct tenant — proven on deployed dev
with two tenants, not asserted. (b) The AMBIGUOUS case (one customer phone, two tenants, both messaged
in-window) resolves per the ruled tie-break or fails CLOSED, and is visible as its own bucket rather
than as a silent pick. (c) A STOP from a customer whose inbound previously resolved to no tenant now
withdraws consent for the right tenant — forced, not incidental. (d) Zero owner action anywhere in the
path. (e) No customer inbound is ever routed to a tenant that never messaged that phone.
