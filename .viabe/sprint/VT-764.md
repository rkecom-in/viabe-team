# VT-764 — a runaway guard that fires on every run and stops nothing

`orchestrator_agent_driver.ORCHESTRATOR_TOKEN_HARD_LIMIT = 10_000`, counted as `tokens_input + tokens_output`
per invocation. The brain's system prompt is ~18k tokens, so `cumulative_tokens > 10_000` is TRUE after the
first call of every run. The check runs inside `check_mid_invocation`, called from the callback; the raise
propagates into langchain's callback machinery, which **catches handler exceptions and logs
`Error in <handler> callback:`** unless `raise_error=True`. Net: an ERROR log line per LLM/tool boundary per
run, and no abort. The manager domain passed 86.8% in the same window, so the runs plainly complete.

Two defects, pick both: (1) the limit was sized before the prompt grew (VT-617 raised the tool-call limit
5→10 for the same "reframed role" reason and left tokens at 10k); (2) the guard's failure mode is silent —
a guard that cannot abort should not exist. Fix: size the token axis to what the role actually spends
(input is prompt-dominated and not a runaway signal; guard OUTPUT + tool calls + wall clock), and make the
breach path either abort or be a metric, not a swallowed exception. Also decide whether the noise is
hiding real errors in the log stream (it is the loudest line in the window).
