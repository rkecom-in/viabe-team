# VT-766 — the abort is recorded, the reason never is

## The measurement

```
pipeline_runs WHERE status = 'aborted_hard_limit', by day (dev)
  2026-08-17 n=4 · 2026-07-03 n=1 · 2026-06-30 n=23 · 2026-06-28 n=16
  2026-05-26 n=1 · 2026-05-24 n=1 · 2026-05-23 n=2 · 2026-05-21 n=7   … 74 total

pipeline_steps WHERE step_kind = 'aborted_hard_limit'
  0 rows. Ever.
```

74 runs died on a hard limit and **not one of them recorded which axis, what was observed, or against
what limit.** `dispatch.py:_write_aborted_hard_limit` builds exactly that envelope — `axis`,
`observed`, `limit`, `reason=hard_limit_exceeded:<axis>` — and its `write_step` is wrapped in a swallow
(`"dispatch_brain: aborted_hard_limit write_step swallowed"`). So either it always fails, or it is
never reached on the path that sets the run status.

**This is VT-764's own defect one layer along: the observability of the guard is silent in exactly the
way the guard was.** A guard you cannot diagnose after it fires is a guard you will misread — and I did
misread it, which is how this row exists.

## What is NOT established, deliberately

**Which raiser sets the status without the step.** `dispatch_brain` runs with `_NullDriver`, which has
no post-invocation enforcement, so its only limit raise came from the callback — and that was swallowed
until VT-764. Candidates for the 74: `OrchestratorAgentDriver.invoke`'s pre-invocation DEPTH check and
`_enforce_post_invocation` (wall-clock / cost), both of which raise outside any callback; or an older
build; or another call path entirely.

I am not naming one. The reason this row exists is that I asserted a branch "had never once executed"
without checking, and the fix for that is not a better guess.

## Scope

1. **Identify the raiser** — from the 74 runs' own rows (tenant, timing, which surface opened the run),
   not from reading the code and inferring. The 4 dated 2026-08-17 are at 13:10–13:14Z and came from a
   local realdb test run, which is a reproducible starting point.
2. **Make the envelope land, or make its absence loud.** A swallow around the only diagnostic write for
   a fatal outcome is the wrong trade: if `write_step` cannot record an abort, that itself is worth an
   ERROR with the axis in the message, so the log carries what the table lost.
3. **Backfill nothing.** The 74 historical aborts have no recoverable axis; say so rather than inferring
   one.

## Exit gate

(a) A forced abort on each axis writes an `aborted_hard_limit` step whose envelope names the axis,
observed and limit — proven by forcing it, not asserted. (b) A `write_step` failure on that path emits
an ERROR carrying the axis, so the reason survives even when the row does not. (c) The raiser behind the
74 is named with evidence from the run rows. (d) A test pins that the step is written for a
callback-originated breach, which VT-764 made reachable for the first time.

## Relationship

- **VT-764** — fixed the guard's ability to abort and mis-sized axis; this row is the reason you cannot
  currently tell what any past abort was.
- The correction to VT-764's own claim ("the branch had never once executed" — wrong, 74 runs) lives in
  that row's build log.
