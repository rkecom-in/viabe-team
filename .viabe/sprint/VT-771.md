# VT-771 — the choke asks who is sending, and the answer is hardcoded

## The mechanism, in one signature

```python
def assert_customer_send_allowed(
    tenant_id: UUID | str,
    *,
    agent: str = "sales_recovery",   # <- the whole row
    ...
```

`assert_customer_send_allowed` is **the** deterministic pre-gate for every customer-send path. It
takes the sending agent's identity as a caller-supplied string with a **default**, and it uses that
identity for three consequential things: the VT-619 per-tenant×agent budget bound
(`budget_status(tid, agent)`), the Gate-0 activation bar (`is_agent_eligible(tid, agent)`), and the
attribution on the hard-cap incident it emits.

## This is already wrong, on both live call sites

Neither caller is a sales_recovery send, and both pass the literal anyway:

| call site | what it actually is | what it declares |
|---|---|---|
| `campaign/execute.py:364` | an approved **campaign** send | `agent="sales_recovery"` |
| `integrations/customer_inbound.py:167` | a **session opt-in reply** to a customer inbound | `agent="sales_recovery"` |

So campaign sends are metered against sales_recovery's token budget and admitted by sales_recovery's
activation bar. A tenant who has crossed sales_recovery's bar can run campaigns they were never
gated for; a tenant who exhausts sales_recovery's budget silently loses campaigns too. Neither
behaviour was decided — it is what a default parameter did.

**The default is the more dangerous half.** A literal at a call site is at least visible in review.
A default means a NEW specialist that simply forgets the keyword gets sales_recovery's budget and
sales_recovery's eligibility, silently, and the send succeeds — which is the worst possible failure
direction for a gate. P2.1 (lead win-back), P2.2 (campaigns) and P2.3 (checkout rescue) all add
callers. This must be fixed before they land, which is exactly what Clau rostered.

## The identity already exists in the database — that is why the fix is small

`agent_draft_batches.agent TEXT NOT NULL` (migration 126) records the specialist that produced the
draft. Where a send descends from a persisted draft, the choke should read the identity **from the
row it is about to act on** rather than accept a claim from its caller. A gate that trusts its caller
to say who is calling is not a gate; it is a convention.

## THE TRAP — do not delete the default first

`activation_registry.REGISTRY` currently holds exactly **two** entries: `sales_recovery` and
`integration_agent`, and `is_agent_eligible` **fails closed for an unregistered agent**. So passing
the honest identity (`campaigns`, `lead_winback`, `checkout_rescue`) BEFORE those agents have
registry entries converts a wrong-but-passing gate into a right-but-failing one: campaigns would stop
sending entirely, on a change whose whole point was correctness.

**Build order, binding:**
1. **Registry entries + declared prereqs first** for every identity that will reach the choke. This is
   FIRST-PROOF **P2.6** — so VT-771 and P2.6 are coupled and P2.6's registry half comes first.
2. **Then** resolve identity from the persisted draft at the choke, for draft-descended sends.
3. **Then** make `agent` a required keyword — delete the default — and fix both existing call sites to
   declare what they actually are.
4. **Only then** are P2.1/P2.2/P2.3's call sites safe to add.

Doing 3 before 1 is a self-inflicted outage. Doing 1 without 3 leaves the default in place and the
next specialist still inherits sales_recovery's bar by forgetting a keyword.

## Exit gate

(a) `assert_customer_send_allowed` has **no default** for `agent` — a caller that omits it is a
TypeError at import-time-adjacent call sites, not a silent sales_recovery send. (b) For a
draft-descended send the identity is READ from `agent_draft_batches.agent`, and a caller-passed
identity that DISAGREES with the persisted row fails closed and is recorded — the disagreement is the
signal. (c) Every identity reaching the choke has a REGISTRY entry with declared prereqs; an
unregistered identity still fails closed (unchanged). (d) Campaign sends are metered and gated as
campaigns, proven by a budget/eligibility read that names the right agent — not asserted. (e) The two
existing call sites declare what they are, and a test pins that no call site in `src/` passes a
literal that contradicts the draft it is acting on.

## Not in scope
`wa_send_allowed`'s owner-action dependency (VT-765 raised it; still Fazal's). The choke's gate STACK
is unchanged — this row changes only **who the gate is told it is gating**.
