# VT-775 — the funnel exists, and the front door does not open onto it

## Measured, not assumed

| URL | status |
|---|---|
| `https://viabe-team.vercel.app/team/signup` | **200** — the prod team app is LIVE and serving signup |
| `https://viabe-team.vercel.app/team` | **200** |
| `https://viabe.ai/team/signup` | **404** |
| `https://viabe.ai/team` | **404** |
| `https://viabe.ai` · `https://viabe.ai/reports` | 200 (served by the `viabe-web` project) |

Vercel holds four projects under `rkecom-projects`: `viabe-web` (serves `viabe.ai`), `viabe-team-web`
(prod team app, updated 8h ago), plus the two dev projects. **`viabe.ai` is owned by `viabe-web`, so
`/team/*` never reaches `viabe-team-web`.**

**Correction to CLAUDE.md:** it records the prod Vercel project `viabe-team-web` as *"not yet created
— creation + deploy wiring = VT-231 cutover scope."* It exists and it is deployed. VT-231 itself is
the **Supabase Mumbai** row, not the web one; there was no row for this at all, which is why the gap
survived to be found at P1.1.

## Why this blocks P1.1, and why the vercel.app URL is not a workaround

P0.5 requires RKEcom to onboard **through the real funnel, not seeded**, and
**CL-2026-08-20 makes RKEcom a pure tenant** — treated exactly as a stranger's business. A stranger
does not sign up at `viabe-team-web.vercel.app`. Onboarding through the raw Vercel URL would produce a
tenant row and prove nothing about the funnel a real owner walks, which is the same class of mistake
as the VT-725 canary that passed on a path no live turn takes.

So the vercel.app URL is available and is **deliberately not** being used to unblock this.

## Fazal's tap (the whole row)

Route `viabe.ai/team/*` to the `viabe-team-web` project. Two shapes, his call:
1. **Rewrite on `viabe-web`** — `/team/:path*` → `viabe-team-web`. Keeps one apex domain; the Reports
   site keeps serving everything else. Touches a live customer-facing project's config.
2. **Domain/path assignment on `viabe-team-web`** in the Vercel dashboard.

**Why this is not CC's to take despite CC having Vercel access:** `viabe.ai` is a live customer-facing
domain serving Viabe Reports. A routing change there can take the Reports site down, and that is
prod-impacting and outward-facing in the CL-431 sense. CC will execute it the moment Fazal says which
shape and authorizes it — **the config change itself is small; the authority is the gate.**

### The REAL blocker for signing up on prod — Fazal's, under CL-431

**`NEXT_PUBLIC_TEAM_LAUNCH_MODE` does not exist on the `viabe-team` (prod) project at all.**
`launchMode()` therefore returns `waitlist`, and `/team/signup` on prod redirects to the "Coming
soon" page. Measured: `viabe-team.vercel.app/team/signup` returns 200 and renders the waitlist, not
the form.

Prod signup is unreachable until that variable is set to `live` on the prod project. That is a prod
env-var change and therefore Fazal's, not CC's. Verified from a temp directory so the repo's
`.vercel` link was never modified.
