# VT-747 — the owner's authoritative decision, undone by a status message

## The defect

`runner.try_resume_pending_approval` wraps the whole resolution in one transaction:

```python
with tenant_connection(tenant_id) as conn, conn.transaction():
```

Inside it, `agent/approval_resume.py::_ack_owner_stalled_campaign` runs a raw
`SELECT owner_phone FROM tenants` **on that same connection, with no SAVEPOINT**.

A server-side error there aborts the owner's transaction. The function's fail-soft `except`
swallows the Python exception, so nothing surfaces — and the COMMIT silently becomes a ROLLBACK.

## Why this is the worst shape available

The owner's approval is **authoritative** (Pillar 7). This path exists to guarantee that an approval
is never resolved into silence. A failure here does the opposite of its own purpose: the owner said
yes, the system told them nothing was wrong, and the decision was quietly discarded — with the
fail-soft handler ensuring nobody finds out.

It is not hypothetical. **This exact hazard is why a VT-740 wake-gate attempt was rejected**
(recorded in VT-740). I savepointed my own addition at the time and deliberately left this
pre-existing one alone, because wrapping it changes behaviour on the send-ack path and belongs in
its own row. This is that row.

## Scope

1. Wrap the read in a nested `conn.transaction()` (SAVEPOINT), matching what
   `_report_effect_on_redrive` already does — so a failure rolls back to the savepoint and the
   owner's resolution survives.
2. **Audit the whole enclosing transaction for siblings.** This is one instance of a class: any
   other statement executed on the resolve connection has the same power to silently unwind the
   approval. Enumerate them; savepoint or move each.
3. Consider whether the ack belongs on the resolve connection at all — an owner-facing status
   message arguably should not share a transaction with the decision it reports.

## Boundaries

- **Never widen the fail-soft `except` into a bare pass that hides a rollback.** The current
  swallow is exactly what makes this invisible; the fix is scoping the failure, not hiding it better.
- The owner's resolution must commit even if every ack fails. That is the invariant.

## Exit gate

(a) A forced server-side error inside the ack leaves the approval RESOLVED and committed — proven by
forcing the failure, not by reading the `except`. (b) Every other statement on the resolve
connection is enumerated and either savepointed or shown safe. (c) A regression test drives the real
`try_resume_pending_approval` with a failing ack and asserts the resolution persisted.
