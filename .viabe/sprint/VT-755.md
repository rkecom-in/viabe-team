# VT-755 — the Manager parked waiting for an answer to a question it never asked

## The evidence, verbatim from `pending_questions` on dev

**Read the CORRECTION section below before quoting any of this.** These rows exist in the database; they
were never delivered to the owner.

```
task 9d1f6839   status=waiting_owner   stall_metadata: (EMPTY)

q 77e7004f  ANSWERED  asked 12:19:58  answered 12:26:07
   "I couldn't build the win-back campaign yet because some information is missing.
    Could you help with this: Provide a valid evidence source for this run or register
    the Sales Recovery retrieval tools.?"
   owner answered: "haan theek hai, bhej do unhe"

q 1b2f80c4  OPEN      asked 12:26:40  answered NULL
   ...THE IDENTICAL QUESTION, 33 SECONDS LATER.
```

Tenant `d693785a`, scenario `sr_l2_owner_approval_gates_send`, 748s, terminal. Final state:
`campaigns=0`, `pending_approvals=0`, `sends=0`, task `waiting_owner`.

## CORRECTION before anyone acts on the above — the question was NEVER DELIVERED

My first reading of this was "an engineering string was sent to a shop owner." **That is wrong, and the
truth is worse.** `conversation_log` for the same tenant, which is the whole of what the owner saw:

```
12:19:13  owner      purane customers ko wapas laane ke liye ek accha sa offer draft kar do unke liye
12:21:47  assistant  Got it — I'm on it and I'll update you shortly.
12:23:35  owner      haan theek hai, bhej do unhe
12:28:25  assistant  Got it — I'm on it and I'll update you shortly.
```

Four messages. **Neither question appears.** The owner received two identical D1 acks and nothing else,
ever.

So the engineering-string leak is **LATENT, not observed** — it would fire the moment a delivery path
exists, and it must still be fixed, but nobody has read it yet. What actually happened is two different
and sharper defects:

**`pending_questions` HAS NO EMITTER.** The whole surface is `ask()` (INSERT, `review.py:495`),
`get_open()` (`triage_seam.py:506`), `correlate_reply()` (`:738`), `get_latest_answered()`
(`workflow.py:588`), and the DSR purge. **Nothing sends the question text to the owner.** The
owner-clarification ledger is write-and-correlate only. This is the seventh instance this week of the
same class — a row written, a reply correlated against it, and the thing itself never emitted.

**THE OWNER'S MESSAGE WAS CONSUMED AS AN ANSWER TO A QUESTION THEY NEVER SAW.** At 12:23:35 the owner
said *"haan theek hai, bhej do unhe"* ("yes fine, send it to them") — spontaneously, having received
only "I'm on it". `correlate_reply` bound it to the undelivered question and stamped it `answered` at
12:26:07. The owner's ACTUAL intent — an instruction to send — was silently discarded as the answer to
a question about registering retrieval tools. `correlate_reply` selects the oldest open question for the
tenant with **no check that the question was ever delivered**, so any owner message can be swallowed by
an invisible question.

That is the money-path shape of this row: an owner said "send it" and the system recorded it as
clarification. Nothing was sent (`sends=0`), so no wrong send happened here — but the mechanism that
discarded the instruction is the same one that would mis-read the next one.

## The mechanism, file:line

`manager/review.py:311-325`. When the SR specialist returns `missing_data`, the Manager composes the
owner question out of the specialist's **`suggested_remediation` field, verbatim**:

```python
remediations = [r for r in (str(item.suggested_remediation or "").strip() for item in plan.missing_data) if r]
if remediations:
    asks = "; ".join(remediations)
    return PlanSpecialistReturn(
        status="needs_owner_input",
        owner_question=("I couldn't build the win-back campaign yet because some information is missing. "
                        f"Could you help with this: {asks}?"),
        ...)
```

`suggested_remediation` is an **engineering** field. Nothing asks whether its contents are something a
business owner could conceivably do. The branch immediately below is already the correct destination for
this case — no remediation ⇒ `blocked` with no proposed outcome ⇒ **ESCALATE**, which its own comment
calls "an honest closure". An engineer-shaped remediation string is precisely what should take that
branch, and instead it takes the owner one.

The design comment above it is right and the implementation misses by one predicate: *"Missing data is
the owner's to supply, so this is exactly what `needs_owner_input` exists for."* True — but the
specialist can classify an **infrastructure** gap as `missing_data`, and then infrastructure remediation
gets read to the owner as if it were their missing data.

## Five defects. Do not conflate them.

**0. `pending_questions` has no emitter — the ask is a DB row nobody sends.** OBSERVED. This is the
defect that makes the D1 "I'll update you shortly" a broken promise on this path: the Manager parks the
task waiting for an answer to a question the owner was never asked, so no answer can ever come. Highest
priority of the five and entirely decision-independent.

**1. `correlate_reply` consumes an owner message as the answer to an undelivered question.** OBSERVED,
and the most dangerous of the five. It picks the oldest open question for the tenant and never checks
that the question reached anybody, so the owner's real instruction ("send it to them") was recorded as
clarification and discarded. Any owner message can be swallowed by an invisible question. Fixing (0)
does not fix this: even with delivery working, a message that arrives before the question is delivered
must not be treated as its answer.

**2. An engineering string would reach an owner.** LATENT — the text exists in `pending_questions` but
was never delivered, so no owner has read it. Still a real O0 / Manager-voice breach the moment (0) is
fixed: the Manager is ONE entity with one voice, and "register the Sales Recovery retrieval tools" is not
something that entity says to a shop owner. **And note the string is MODEL-AUTHORED** —
`suggested_remediation` is a required field on the model's own `CampaignPlanInsufficientData` variant
(`campaign_plan.py:267`), so this is unvalidated model output being spliced into owner copy, not a
hardcoded internal error escaping. Fix (0) and (2) together or the fix ships the leak.

**3. An unanswerable question is asked at all.** Even phrased perfectly, no owner can register a
retrieval tool. When the remediation is not owner-actionable the Manager must ESCALATE (to ops/Fazal),
not ask. The branch exists; the routing predicate is missing. Decision-independent.

**4. Identical re-ask with no no-progress detection.** Answered at 12:26:07, re-asked at 12:26:40 with
byte-identical text. Nothing compares a new question against the just-answered one, so an owner can be
asked the same unanswerable thing forever. This is the loop/stall disease in its purest form — and note
VT-606 already fixed a neighbouring instance (CLARIFY with no question text → REVISE), so this is the
same class recurring at a different predicate. Decision-independent.

**4. THE IMMORTAL PARK — the structural one, and the most dangerous.** That task can never move and
never alerts:

| escape route | why it is closed |
|---|---|
| `_wake_waiting_workflow` (VT-671) | fires only from `mark_approval_resolved`, and `pending_approvals=0`. Also needs `stall_metadata.wait_workflow_id`, and **`stall_metadata` is EMPTY** — the "pre-VT-671 park (no stamp) — the poll ladder covers it" path |
| the retry ladder / orphan reaper | `waiting_owner` is **deliberately EXCLUDED** from the sweep's active set (`task_store.py:280`) so the ladder cannot burn an awaiting-approval task to dead_letter — correct for approvals, and it means a question-parked task is untouchable |
| `pending_questions.correlate_reply` | only flips the row to `answered`. It sends **no** DBOS wake |
| an alert | none. Nothing fires |

So: **`waiting_owner` + no pending approval + no wake stamp = a task that is immortal, silent, and
invisible to every recovery seam we have.** That is a task-class hole, not one bad run.

## Root cause of the `insufficient_data` verdict: OPEN. Three hypotheses tested and REFUTED.

The remediation text tempts a diagnosis — *"Provide a valid evidence source for this run or register the
Sales Recovery retrieval tools"* — and I chased three readings of it. **All three are wrong. Recording
them as refuted so nobody re-chases them:**

| hypothesis | verdict | evidence |
|---|---|---|
| SR's retrieval tools are unregistered, so it has no evidence source | **REFUTED** | SR is context-in / plan-out **by design**. `tools=[]` on the test branch and no `tools=` on the live `messages_call` are correct: the evidence arrives in the `SalesRecoveryContext` bundle (`dormant_cohort`, `customer_ledger_summary`, `recent_campaigns`, `attribution_snapshot`). There are no retrieval tools to register. **The remediation string is model-invented, not a real system diagnostic** |
| shared root cause with VT-752's `evidence_refs: too_short` | **UNSUPPORTED** — withdraw the link | it rested entirely on the hypothesis above |
| the CL-425 owner-inputs gate was closed, so `dormant_cohort` was safe-emptied | **REFUTED** | the gate is `tenants.owner_inputs` (a boolean, via `l0_writer._owner_inputs_enabled`) and for this tenant it is **TRUE**. All 6 re-drive tenants have it TRUE |

**And the tenant genuinely had a cohort:** 8 customers, 8 with `record_of_consent`, 8 `entry_type='sale'`
ledger rows, and **6 lapsed more than 45 days**. So the SR brain returned `insufficient_data` *while the
evidence existed and the gate permitted reading it.*

**The open question, with the pointer rather than a guess:** `review.py`'s own comment on this exact
branch already says *"(the cohort read is separately flaky — RV-1)"*. So the next step is to instrument
`detect_lapsed_customers` / `db.wrappers._LAPSED_CANDIDATES_SQL` for this tenant shape and find out why a
6-candidate cohort surfaced as zero — **not** to theorise a fourth cause. I have been wrong three times
on this and the pattern is that the remediation text is model prose, so reading it as a diagnostic is the
mistake.

Note this does NOT weaken defects 0-4: every one of them is verified independently of why the specialist
said "insufficient data". They are what turns a recoverable cohort-read miss into a silent permanent
stall that eats the owner's instruction.

## Scope

0. **Give `ask()` a delivery path, or stop calling it an ask.** The question must reach the owner
   through the single Manager emission choke (never a second send path — the Manager is ONE voice), and
   the task must not park `waiting_owner` unless delivery is confirmed. A park waiting on an
   undelivered question is a guaranteed stall.
0b. **`correlate_reply` must refuse to answer an undelivered question.** Require a delivery stamp on
   the question row before any inbound can be bound to it; an inbound arriving with no delivered
   question falls through to normal dispatch, where "haan theek hai, bhej do unhe" is read as what it
   is. This is the half that protects the owner's intent.
1. **Gate `suggested_remediation` before it becomes owner copy.** Owner-actionable ⇒ ask.
   Not owner-actionable ⇒ take the existing escalate branch. Decide by a positive test on the
   remediation's shape, and **do not build a keyword blocklist of engineering phrases** — that is an
   undefined-possibilities list (STANDING, Fazal 2026-07-15). Prefer a structural signal: the
   `missing_data` item's own `category`, plus an LLM judgment on owner-actionability with escalate as
   the fail-closed default.
2. **No-progress detection on re-ask.** A question must not be asked when an identical/equivalent one
   was just answered without the task advancing. On no progress: escalate, don't re-ask.
3. **Close the immortal-park hole.** Every `waiting_owner` task needs exactly one of: a resolvable
   approval, a wake stamp, or a deadline after which it alerts. A parked task with none of the three is
   the defect — detect it and page, reusing VT-746's now-writable alert path.
4. **Find out why a 6-candidate cohort surfaced as zero.** Instrument
   `detect_lapsed_customers` / `db.wrappers._LAPSED_CANDIDATES_SQL` against this tenant shape (8
   customers, 8 consents, 8 sales, 6 lapsed >45d, `tenants.owner_inputs` TRUE). `review.py`'s own
   comment on this branch already calls the cohort read flaky (RV-1). Do NOT read the model's
   remediation prose as a diagnostic — three hypotheses drawn from it were refuted (see above).
5. Re-drive `sr_l2_owner_approval_gates_send` after (1)-(4) and show the question the owner would now
   receive, or the escalation that replaces it.

## Boundaries

- **Do not silence the question by making the Manager guess.** Proceeding without the missing evidence
  would produce an ungrounded campaign — exactly what the `evidence_refs` gate correctly refuses. The
  fix is to escalate, never to fabricate.
- **Do not weaken the approval gate.** Note what did NOT go wrong here: `sends=0`. Nothing was sent
  without approval. This chain is a reliability and owner-quality defect, not a safety one.
- Do not remove `waiting_owner` from the reaper's exclusion — that exclusion protects the 48h approval
  TTL (the VT-668 incident). Add a separate detector; do not widen the ladder.

## Exit gate

(a) No owner-facing question can contain an engineering remediation — proven by driving the specialist's
own `missing_data` path with a non-owner-actionable remediation and asserting an ESCALATION, not an ask.
(b) An answered question followed by no task progress escalates instead of re-asking, proven by
execution. (c) A `waiting_owner` task with no approval and no wake stamp raises an alert — proven by
forcing that state, not by reading the detector. (d) `sends=0` still holds on the re-drive: this row
must not buy reliability with safety.
